# Beacon 手机执行渠道方案

更新日期：2026-11-06
状态：WhatsApp 本人会话已完成一次真实发送回填；多渠道开发版已实现并进行模拟验证，其余平台尚待用户安排实机验收。

当前代码、平台差异和验收范围见 [多渠道实施计划](../plan/mobile-multichannel.md)，构建与配对见 [手机端说明](../apps/mobile-agent/README.md)。后文包含目标设计，不代表所有能力已经完成真实验证。

## 1. 目标与定位

让销售人员在 Beacon 中准备消息、确认发送，由已绑定业务账号的 Android 手机执行社媒操作，并将发送结果和客户回复回填到同一门店。

首阶段作为 Beacon 的一种执行方式，不另建独立 CRM，不替换已经可用的 Gmail 服务及 Meta API。手机操作能够覆盖部分 API 无法覆盖的使用场景，但不能保证所有平台、账号和收件人均可联系，也不能消除平台限制、登录异常和界面变更带来的风险。

| 路径 | 适用场景 | 在 Beacon 中的位置 |
| --- | --- | --- |
| Gmail API | 邮件发送和回复同步 | 保留现有能力 |
| Meta API | 已接入账号及平台允许的会话回复 | 保留现有能力 |
| 手机执行 | 官方客户端中可实际完成的联系与回复 | 新增执行方式，先验证一个渠道 |
| 人工联系 | 自动执行无法识别或需要人工操作 | 同一任务中接管、记录结果 |

本方案的核心不是“能自动点击”，而是可靠完成 **选对账号和客户 → 发送确认的内容 → 确认结果 → 收到回复 → 继续跟进**。

## 2. 首轮范围

使用一台专用 Android 手机、一个业务账号、一个渠道，以及自有或明确同意参与测试的收件人。WhatsApp 可作为候选，但应先验证当前设备上的实际收发能力，再确定首个渠道。

首轮仅支持普通文字消息、实际会话读取、回复回填、异常接管。不做多设备调度、图片与文件发送、群发、自动营销跟进、本地大模型或独立商业化平台。

Facebook、Instagram、LinkedIn、TikTok 分别验证；某个渠道成功不能推定其他渠道也可用。公共主页 URL、用户名、电话号码只是定位信息，不能直接视为已确认的聊天对象。

## 3. 用户怎样使用

### 3.1 绑定手机和账号

设置中增加“手机与账号”。管理员通过一次性配对码绑定设备，销售人员在手机官方客户端自行登录。页面显示设备在线状态、绑定账号、所属人员和最近同步时间。

账号登录、验证码和平台异常由用户在手机处理，Beacon 不收集社媒密码。当前开发版直接使用官方 App 当前登录的社媒账号，无需重复填写 FB 等账号信息；WhatsApp 本方号码仍用于本人会话核对。系统不读取密码、不自动切换账号，也不宣称已自动识别账号身份。

### 3.2 发送消息

用户仍在现有门店详情或沟通工作台选择联系方式、编辑 AI 草稿并预览。选择“手机执行”后，预览中明确显示发送账号、目标客户及消息内容，点击一次“确认发送”即可提交。

目标体验是不增加每封消息都必须在手机再次确认的流程。当前开发版仍由用户主动领取并逐条确认，待各平台实机验收后再评估简化；发现账号不一致、目标不明确或界面异常时暂停并提示手机处理。

任务页面用业务语言显示：等待手机、正在执行、已发送、结果待确认、需要处理。技术日志放在详情中。缺少手机或目标不可联系时直接说明原因，不让用户面对空白列表或不可解释的灰色按钮。

### 3.3 收到回复

当前开发版由用户在手机选择执行记录，尝试读取当前会话的可识别入站文字，或手动粘贴；核对确认后回填。尚未实现无人值守回复巡检。回复进入现有“客户会话”，门店状态更新为“已回复”。AI 可总结回复并起草下一条消息，用户确认后发送。

通知仅作为有新消息的线索；必须读取并匹配实际会话后才能标记已回复。不得把打开应用、收到通知或自己发送的消息计为客户回复。

## 4. 架构与边界

沿用现有 FastAPI、Next.js、PostgreSQL、用户权限、门店分配、消息确认和 AI 配置体系。

| 模块 | 职责 |
| --- | --- |
| Beacon API 与数据库 | 保存任务、确认快照、设备绑定、执行结果和会话；作为业务状态唯一依据 |
| 手机执行适配层 | 对接现有任务和消息流程，管理领取、取消、超时、恢复和结果回填 |
| Android 客户端 | React Native + Expo development build；本地 Android 模块负责跨应用操作与持久化执行日志 |
| 渠道适配器 | 分别实现账号识别、定位客户、发送、结果核对和回复读取 |
| 设备通信 | 首版采用 HTTPS 领取任务、心跳与结果回填；有明确规模需求后再评估 MQTT |
| AI runtime | 复用现有模型配置，提供必要的界面理解、回复理解和文案生成 |

MQTT 是候选传输方式，不是业务任务数据库。首轮先验证连接、后台运行和恢复能力，再决定是否引入 broker；不预先绑定 EMQX 或其他产品。引入依赖前核对具体版本许可证和维护成本。

若采用 MQTT：使用 TLS、每设备独立凭据和主题权限，不使用 retained 消息保存发送命令。QoS 1 允许重复投递，因此收到消息或 ACK 只能证明传输进展，不能证明业务消息发送成功。

Android 的 Accessibility、Intent 和截图识别是候选技术组合，具体可读内容和可执行动作需要逐应用验证。不要假设所有页面均提供稳定控件、深链接或消息 ID。

## 5. 可靠执行与防止重复发送

每次发送绑定以下快照：任务 ID、工作空间、门店、负责人、渠道、发送账号、目标会话或联系方式、内容版本及 hash、用户确认时间。修改收件人或正文后重新确认。

执行过程：

1. 手机领取任务并获得有效执行租约，同一设备同时只操作一个前台任务。
2. 核对当前登录账号、目标会话和消息内容。
3. 在点击发送前向服务器检查任务是否取消、归属是否改变、确认快照是否仍有效。
4. 本地持久化“准备执行发送”记录，然后执行发送动作。
5. 读取会话中的结果，保存观察证据并回填服务器。

任务状态建议如下：

| 状态 | 含义与恢复方式 |
| --- | --- |
| 待执行／等待设备 | 尚未开始，可取消或安全重新领取 |
| 执行中 | 设备持有租约，其他设备不能同时执行 |
| 已发送 | 已观察到与目标、内容匹配的发送结果 |
| 结果待确认 | 可能已点击发送，但没有可靠结果；先核对会话，不自动重发 |
| 需要处理 | 登录失效、目标歧义、页面改变等；人工处理后继续 |
| 已取消／失败 | 明确未发送时结束，保留原因与历史 |

数据库唯一约束和设备本地日志共同处理重复任务。租约需有代次标识，拒绝过期执行器继续领取或提交错误状态。租约过期不代表消息未发送，不能直接把存在发送疑问的任务转交另一台手机重发。

取消在发送动作前生效；若动作已发生，应报告实际结果，不能承诺撤回。断网发生在发送后时，手机先保存结果，恢复连接后上报。人工接管期间暂停自动操作，接管结束后重新核对状态。

“已发送”“已送达”“已读”分开记录，只展示实际观察到的状态。不伪造平台消息 ID；没有稳定 ID 时使用内部记录编号并注明证据来源。

## 6. 回复同步与会话归属

只处理明确绑定的业务账号和业务会话，不扫描手机全部个人聊天。

会话关联以“渠道＋本方账号＋对方身份”为基础，再关联门店。首次匹配存在重名或多个门店时由用户选择一次，后续复用绑定；不能仅凭显示名称自动归属。

首版采用通知触发检查和受控的会话检查任务。由于手机前台执行串行，回复读取与发送共享队列；展示最近检查时间，不承诺始终实时同步或完整恢复无限历史。

每条消息保存方向、正文、可获取的平台时间、系统观察时间和来源。优先使用可靠消息标识；无标识时结合会话、方向、时间、内容和重叠读取范围去重。相同文本可能是不同消息，不能仅按正文 hash 合并；无法确定时保留待核对状态。

客户拒收等结果接入现有抑制和跟进流程。AI 判断不确定时显示建议，不凭模型猜测写入“客户已回复”或“已经发送”。

## 7. AI 的作用

优先使用确定性页面规则和控件定位，AI 用于规则难以覆盖的界面理解、联系人辅助识别、回复摘要及草稿生成。执行器负责校验账号、收件人、正文和动作范围。

聊天内容和页面文字是待处理数据，不能作为指挥执行器改变目标或发送内容的指令。模型输出必须通过结构校验，不允许任意自由点击、切换账号或自行决定联系客户。

复用 Beacon 的服务端 AI runtime，记录用途、模型版本、耗时和失败原因。只上传当前任务所需的局部信息；模型密钥不下发手机。本地 LLM 待准确率、延迟和设备成本有实测数据后再考虑。

## 8. 权限与运行维护

- 复用管理员、销售总监和业务成员权限，设备可执行范围与门店归属一致；转交门店后重新检查未执行任务。
- 设备凭据可撤销，配对码短期有效；丢失设备可立即停止领取任务。
- 使用专用业务设备，截图和会话证据限定访问范围、保留期限及删除方式，不保存无关聊天内容。
- 记录应用版本、设备状态、步骤耗时和失败阶段，敏感凭据不进入日志。
- 验证锁屏、后台限制、网络变化、应用升级及人工操作冲突；不能依赖“进程常驻”假设保证成功。
- 不通过验证码绕过、伪装身份或规避平台限制维持运行；遇到此类状态停止自动任务并交由账号使用者处理。

## 9. 分阶段实施与验收

### 第一阶段：技术探索

确认一台设备和一个渠道，实测账号识别、联系人定位、文字输入、发送结果读取、回复读取和后台恢复。产出操作记录、适配限制和依赖许可证清单。

若关键页面无法可靠识别或发送结果无法核对，先缩小为“打开会话并填入草稿、人工完成发送”，不把不可靠路径包装成自动发送。

### 第二阶段：单设备 POC

建议验收样本：至少 20 次受控发送、10 条受控回复，并覆盖下列故障。正常路径自动完成率目标为 95% 以上；样本规模有限，只用于决定是否继续，不能当作生产可靠性承诺。

| 验收场景 | 必须看到的结果 |
| --- | --- |
| 正常发送与回复 | 正确账号、正确对象、准确正文，回复进入对应会话 |
| 同一任务重复投递 | 不重复发送 |
| 发送前断网／重启 | 恢复后按日志继续，无错误重复 |
| 点击发送后断网或回填丢失 | 进入结果待确认，核对后恢复，不盲目重发 |
| 错误账号、重名对象、目标不可联系 | 暂停并给出可操作原因，不误发 |
| 取消、门店交接、租约失效 | 发送前拦截过期执行；已发生动作如实记录 |
| 重复通知、相同回复文本、自己的消息 | 不误归属、不漏记独立回复、不误标客户回复 |
| 锁屏、人工接管、应用界面变化 | 可恢复或明确转人工，不无限循环 |

错误收件人和重复发送必须为零；出现一次就定位修复并重新验收。报告同时列出成功、失败、人工介入的分母，以及完成耗时、回复发现延迟、模型调用量和成本，不只展示成功案例。

### 第三阶段：接入 Beacon

复用现有消息预览确认、任务、发送记录和客户会话，增加手机与账号设置、执行方式和异常处理。所有后台状态均可在界面解释，避免配置成功却无法操作。

建议代码位置（尚未创建）：Android 客户端放 `apps/mobile-agent/`；API 执行适配按现有模块边界接入；确需独立通知服务时再放 `services/`。如新增迁移，同步部署兼容性声明与回滚说明。

本地验证完成后由用户自行提交推送，沿用现有 GitHub Actions 发布流程。测试与开发不代表授权向真实客户发送消息。

### 第四阶段：逐渠道扩展

先稳定一条完整收发链路，再分别增加 FB、Instagram、LinkedIn、TikTok 或 WhatsApp。每个渠道独立建立适配版本、测试矩阵、支持范围和回退方式。多设备、设备池、自动调度与本地模型另立计划。

## 10. 技术落地设计（研究建议，尚未实现）

### 10.1 框架选择

建议采用 **React Native + Expo development build + TypeScript + 薄 Android 原生模块**。复用项目的 TypeScript 经验和接口类型，把原生开发集中在跨应用执行能力上，不要求整个客户端使用 Kotlin。

| 方案 | 可复用内容 | 必须额外承担的工作 | 本项目建议 |
| --- | --- | --- | --- |
| React Native + Expo development build | TypeScript 类型、数据校验和纯业务逻辑 | Android 服务、权限、跨应用操作与执行恢复 | 首选 |
| Flutter | 独立移动 UI 与插件生态 | 新增 Dart 技术栈；仍需平台通道与 Android 模块 | 团队已有 Flutter 经验时再考虑 |
| 全原生 Android | Android 系统能力集成直接 | 页面、网络和业务状态需单独实现 | 不作为首版默认方案 |
| Appium／uiautomator2 | 设备操作、定位与自动化测试工具 | 主机、ADB 和设备连接的运维 | 用于探索和回归，不作为独立手机客户端 |

Expo Go 不能加载本项目需要的自定义 Android 服务；必须使用 development build。Expo 支持本地原生模块和配置插件，可本地构建 APK，EAS Build 为可选项。涉及权限、Manifest、服务或原生依赖的修改必须重新构建安装，不能依靠 JavaScript OTA 更新解决。

Next.js 的 Ant Design 页面、DOM 和 CSS 不直接搬到手机；仅抽取无浏览器依赖的类型与纯逻辑。首版不预先创建庞大共享组件库。Flutter 的跨平台 UI 同样不能消除 Accessibility 等原生集成工作。

### 10.2 Android 端边界

客户端页面只保留：设备配对、运行检查、开始／暂停执行、当前任务、异常接管、执行记录。账号登录仍在官方应用中人工完成。

| 层次 | 技术与职责 |
| --- | --- |
| 页面与业务交互 | React Native、Expo、TypeScript；展示设备与任务状态，调用原生执行模块 |
| 原生执行模块 | 本地 Expo Module；Kotlin 或 Java 按兼容性选择，实现 AccessibilityService、受控动作和生命周期管理 |
| 渠道适配器 | 按包名、应用版本、页面特征识别账号与目标；控件定位优先，必要时截图辅助；每个渠道独立版本 |
| 本地执行日志 | SQLite 事务保存领取记录、发送前检查点、动作尝试和待回填事件；执行过程由原生模块统一写入 |
| 凭据 | 使用 Android Keystore 支持的安全存储保存设备凭据；不保存销售人员的平台密码或服务端模型密钥 |
| 通信与恢复 | 明确启动的执行会话内领取任务和发送心跳；本地 outbox 断网重传，服务端按事件 ID 去重 |

原生执行模块应在用户离开 React Native 页面、进入第三方聊天应用后继续管理当前执行会话；不能把可靠执行寄托于 JS 定时器一直运行。必要时使用符合系统要求的前台服务和可见通知，但前台服务不意味着可以随意后台拉起其他应用。

探索基线建议 Android 11（API 30）以上的专用测试机，便于验证 Accessibility 截图接口。该选择是项目测试基线，不是所有设备均可稳定执行的保证。安全窗口、截图频率、后台启动、锁屏和厂商省电策略都需要实测。MediaProjection 如作为后备方案，要另行处理用户授权及会话生命周期。

每台手机同一时刻只执行一个界面任务。用户主动开始运行并保持设备解锁；锁屏、账号改变、验证码或人工抢占时暂停。不要实现静默解锁，也不要把后台常驻作为验收前提。

### 10.3 Beacon 后端与数据模型

沿用 FastAPI、PostgreSQL、现有用户／门店分配、消息确认和 `ai_runtime`。首版在 API 内新增手机执行模块，不另建整套 CRM，也不先增加独立微服务。

现有代码中 `Conversation.last_inbound_at` 必填，`OutreachDelivery` 必须关联会话且 `task_id` 唯一；这些结构服务于已有社媒回复流程。手机首触达不能通过虚构入站消息、伪造平台会话 ID 来复用它们。

建议新增以下持久化对象，命名在开发时确定：

| 对象 | 核心字段与用途 |
| --- | --- |
| 设备 | 工作空间、绑定用户、设备公钥／凭据版本、能力、应用版本、心跳、撤销状态 |
| 手机账号绑定 | 设备、渠道、本方账号标识、最近核对时间；与门店的目标联系方式分开 |
| 手机执行单 | 关联既有业务任务、确认内容快照、目标联系方式、本方账号、状态、取消请求 |
| 执行尝试 | 执行单、尝试 ID、租约与 fencing token、发送前检查点、实际动作时间、结果 |
| 执行事件 | 唯一事件 ID、尝试 ID、设备顺序号、发生／接收时间、证据引用 |
| 手机会话与消息 | 账号及目标身份、关联门店、方向、观察时间、可获得的平台时间与 ID、去重依据 |

业务任务仍是用户操作入口；手机执行单与现有 Gmail／Meta 发送记录通过统一查询结果展示。业务任务重试对应新的执行尝试，不覆盖旧结果。手机会话不强制已有客户入站消息；未来能否与通用会话表合并，应通过迁移设计决定。

### 10.4 通信协议与发送一致性

首版采用设备主动访问服务器的 HTTPS 长轮询／短间隔轮询，配合心跳和指数退避；不要求手机开放公网端口。后台暂停后明确显示离线或暂停，不能将轮询成功等同于渠道可发送。

建议接口分工：

- 管理端创建短时、一次性配对码；设备兑换专属凭据，绑定工作空间与用户，支持撤销。
- `claim` 原子领取执行单，返回租约、执行尝试 ID、fencing token 和冻结快照。
- `heartbeat` 延长有效租约；服务端核查设备、归属与取消状态。
- `preflight` 在最终发送动作前复查目标、账号、确认版本、归属和取消请求。
- `events`／`result` 上传持久化事件和结果，使用唯一事件 ID 幂等处理。
- `messages` 回填限定业务会话内观察到的消息；附件和截图使用受控上传接口。
- 管理端提供暂停、取消、撤销配对和结果核对入口。

最终点击发送前先持久化“准备执行发送”记录。点击后进程崩溃、断网或结果回填失败时，恢复为待核对，不因租约到期重新发送。迟到结果仍归档到原尝试；过期执行器不能更新新尝试状态。取消与点击发送存在不可消除的竞态，界面区分“请求停止”和“已停止”，已经发生的发送如实回填。

这套设计提供幂等领取和回填，不能承诺第三方 UI 的严格 exactly-once 发送。结果无法判定时需要核对会话或人工接管。

### 10.5 开源项目取舍

以下为本次研究发现，不表示已完成源码审计、兼容测试或决定引入。实际采用时固定版本并记录依赖许可证。

| 项目 | 用途及许可观察 | 取舍 |
| --- | --- | --- |
| [Expo](https://github.com/expo/expo) | RN 开发、构建及原生模块工具链 | 首版客户端基础；具体依赖逐项核对 |
| [Appium UiAutomator2 Driver](https://github.com/appium/appium-uiautomator2-driver) | Apache-2.0；配合 Appium 主机控制 Android | 实机探索和回归，验证页面是否可识别 |
| [openatx/uiautomator2](https://github.com/openatx/uiautomator2) | Python 包为 MIT；使用设备端服务，传递依赖另查 | 快速验证收发动作，不直接替代独立 APK |
| [mobilerun-portal](https://github.com/droidrun/mobilerun-portal) | 所查仓库 LICENSE 为 AGPL-3.0；涉及移动执行能力 | 可研究模块边界，不默认复制或嵌入项目 |

不因仓库有演示视频就认定支持 FB／Instagram／LinkedIn／TikTok 的长期稳定收发。首先用测试账号验证当前版本的目标聊天界面、账号识别、发送结果与回复读取，再决定复用范围。

### 10.6 部署、升级与验证

建议目录为 `apps/mobile-agent/`，本地 Expo Module 放其 `modules/`；后端模块放 `apps/api/app/modules/` 下的新手机执行目录。共享协议先采用版本化 JSON 与类型定义，确需两端共用时再提取 `packages/`。

服务器继续使用现有 Compose、PostgreSQL、数据卷及 GitHub Actions。新增数据库迁移必须同步 `infra/deploy/compatibility.json` 实际兼容性声明；回滚不能丢失已发送或结果未知的执行记录。设备密钥、证据保留策略及备份恢复要与现有系统一起设计。

APK 单独构建和签名，记录客户端版本、原生执行协议版本及渠道适配版本；签名密钥存 CI secrets 或受控签名环境，不提交仓库。服务端拒绝不兼容协议的领取请求并给出升级提示。更新前先停止领取，待当前尝试结算；未知结果不能因升级消失。首版可内部安装 APK，后续再评估分发方式。

开发顺序：先用 Appium／uiautomator2 验证一条真实渠道路径，再制作 Expo development build，验证用户切换到第三方应用后的原生执行与恢复，最后接入 Beacon 的确认和回填。模拟测试覆盖租约、重复事件、取消竞态、权限交接、未知结果恢复；真实设备测试覆盖锁屏、断网、进程终止、应用升级和人工操作抢占。

**进入完整开发的门槛：**测试机上能够稳定辨认本方账号与目标、执行受控文字操作、确认结果并读取限定会话。若只能打开聊天并填入草稿，就明确交付该辅助能力，不继续扩大自动执行范围。

## 11. 当前结论与待确认项

当前确认的是产品需求与 Beacon 的集成方向，尚未确认手机执行成功率、各应用可读取范围和长期运行成本。

进入开发前需要确定首个渠道、测试设备与账号，并完成实际技术探索。现有 Gmail／Meta 功能继续保留；本方案不把第三方 API 的限制替换为未经验证的手机自动化承诺。

## 手机客户回复通知（2026-11-06）

新版手机助手“设备与账号 → 客户回复通知”选择需要监听的社媒（本轮先 Facebook）。点击“给 Beacon 开启通知使用权”，在 Android “读取、回复和控制通知”应用列表中开启 **Beacon 手机助手**；这里不是为 Facebook 授权，不需要在系统列表找 Facebook。系统权限由用户手动开启，应用内未选渠道不会采集。

手机后台收到所选渠道的新消息通知后，加密缓存在本机并上传 Beacon，断网后重试。群聊、通知汇总和明确本方消息过滤；普通文本通知进入待确认，不作为明确入站消息自动记录。不开启通知历史扫描，不点击通知、不自动回复、不采集其他应用通知。

网页“触达任务与回复 → 手机回复”显示待关联及新回复数量。首次通知核对正文并选当前负责的同渠道门店会话，点击“确认客户回复并回填”。平台提供稳定会话标识时，可记住关联，后续明确入站消息自动回填到既有事件、进展与 AI 跟进分析；没有稳定标识的仍需确认。用户更换社媒登录账号前解除自己的通知会话关联，已有回复保留。门店交接后旧负责人不自动回填。

通知不是完整会话同步：平台不发通知、隐藏正文、手机离线或被系统限制后台时可能漏收。保留“记录客户回复”的手动入口。自动回填不代表已回复客户，跟进消息仍由用户确认发送。

本机通知队列最多 200 条／7 天，上传成功清除正文并保留短期幂等键；服务端未关联通知副本 7 天、已处理副本 30 天，在通知读写时清理，正式沟通事件沿用原保留规则。没有长期后台运行时不保证到期瞬间删除。

技术实现：Android `NotificationListenerService` + `MessagingStyle`，本地 Expo 模块，Keystore 加密队列；API `/api/mobile/device/notifications`、个人收件箱／稳定会话绑定；迁移 `d181a0010001`。开发及验收见 [计划](../plan/mobile-notifications.md)。网页默认每 15 秒刷新一次，可在手机主动同步。新增迁移后已同步 `infra/deploy/compatibility.json`，不承诺跨迁移回滚。

## 门店联系方式直接准备手机触达（2026-11-06）

1. 线索详情找到 Facebook、Instagram、WhatsApp、LinkedIn、TikTok、YouTube 或 X 联系方式，点击“准备触达”。只有电话号码时，点击“通过 WhatsApp 联系”，核对国际号码后继续。
2. 手机助手保持连接并完成运行检查。网页自动选中唯一在线且安装对应 App 的手机；多台时选择执行手机。AI 起草后直接修改正文。
3. 点击“预览手机触达”，核对手机、当前登录账号、目标和完整消息；“确认并交给手机”直接入队，不再重复准备任务。
4. 在手机领取并核对执行。网页“查看沟通记录”跟踪结果；没有发送入口、需要连接、消息请求及结果待核对会分别显示，不算已发送。YouTube 默认查看联系入口；InMail 等由手机人工处理，不自动付费。
5. 客户回复使用上节通知收件箱；首次关联到该门店后，符合稳定会话条件的新回复可自动回填。通知缺失时仍可手动记录回复。

另一联系方式可单独准备，不因门店已有其他任务而封锁。相同收件人的已有任务会复用并提示查看，避免误发重复消息。邮件继续通过 Gmail。

### 手机触达与人工触达切换（2026-11-07）

线索详情左侧选择一个社媒联系方式后，右侧显示固定收件人和“手机触达／人工触达”。换平台或换联系人仍从左侧选择，右侧不重复选择渠道。切换触达方式保留已编辑消息；保存或预览中等待完成后再切换联系人。

人工触达无需连接手机。预览确认内容后，点击“复制消息”，打开对应主页自行粘贴发送；实际发送后点击“已发送，记录结果”，核对发送时间再确认。只复制、只打开主页或取消记录都不会标记已发送。手机触达继续选择就绪手机并确认入队，结果回到同一门店。署名自动沿用个人设置，必要时展开“署名设置”调整。历史任务放在“沟通记录”中，不改变编辑区标题或阻止准备其他联系人。
