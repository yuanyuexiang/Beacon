# Beacon 最小工具操作手册（v0.1，2026-09-30）

面向单操作者试点。所有业务接口在 `/api` 下且需登录；`/api/docs` 为交互式接口文档（FastAPI 自带）。系统不发送任何消息，所有对外联系由人执行后回填。

## 1 启动

方式一：Docker 一键全套（推荐用于试运行和测试）

```bash
cp infra/.env.example infra/.env        # 填 BEACON_SECRET_KEY、引导账号、模型密钥（可选）
docker compose -f infra/docker-compose.yml up -d --build
```

起来后：工作台 http://localhost:3000，接口文档 http://localhost:8000/api/docs。api 容器启动时自动执行迁移；数据文件在卷 `beacon-data`，数据库在卷 `beacon-pgdata`。容器内没有 Chrome，样稿只生成 HTML（本机运行时才出 PNG）。在容器里跑后端测试：

```bash
docker compose -f infra/docker-compose.yml --profile test run --rm api-test
```

方式二：本机开发（只用 Docker 起数据库）

```bash
docker compose -f infra/docker-compose.yml up -d postgres   # PostgreSQL 16，端口 5433
cp apps/api/.env.example apps/api/.env                       # 填写 BEACON_DATA_DIR（绝对路径）、BEACON_SECRET_KEY、引导账号
cd apps/api && uv sync && uv run alembic upgrade head
uv run uvicorn app.main:app --reload --port 8000
pnpm install && pnpm --filter beacon-web dev                 # 另一个终端，http://localhost:3000
```

首次启动时若无操作者，用 `.env` 中的 `BEACON_BOOTSTRAP_OPERATOR/PASSWORD` 创建首个操作者；之后修改 `.env` 不会再创建。

## 2 登录

`POST /api/auth/login` `{username, password}` → 设置 HttpOnly 会话 cookie（12 小时）。`GET /api/auth/me` 查看当前操作者，`POST /api/auth/logout` 退出。

## 3 批次与名单

不需要手工名单。推荐流程：建批次 → `POST /api/batches/{key}/sync/fsa` `{authority_id, business_type_id: 1, exclude_awaiting: true, sample_n, seed}`（地方当局列表 `GET /api/sources/fsa/authorities`）→ `POST /api/batches/{key}/enrich/overture`（首次按批次范围下载 Overture 地点并缓存于 `BEACON_DATA_DIR/overture/`，只填空缺官网，来源与置信度写入线索）→ `POST /api/batches/{key}/screen`（规则预筛：连锁、咖啡店、机构、酒吧标为排除并注明规则版本；其余留 unchecked 交人工；人工改过的不再覆盖）。工作台「批次与线索」页右上角「自动建名单」抽屉按三步引导。CSV 导入仍可用于客户自有名单。首页为仪表盘（按批次的漏斗、渠道、成本）。

1. `POST /api/batches`：`batch_key`、`country`（如 GB）、`region`、`source_name`（如 fsa）、`source_version`（FSA extractDate）、`source_licence`（OGL-3.0）、`sampling_method`、`sampling_seed`。
2. `POST /api/imports`（multipart：`batch_key`、`file`）：CSV 需含 `name` 和 `fhrsid` / `source_key`(`fsa:416314`) / `source_id` 之一；可选 `address, postcode, lat, lng, website, sample_order, screening_class, screening_reason`。返回逐行错误；同批次重导不新增；已存在门店跨批次关联；不按店名合并。
3. `GET /api/leads?batch_key=`、`PATCH /api/leads/{id}`（官网、筛选分类与原因、法律主体状态与证据；主体默认 unknown）。
4. `GET /api/leads/{id}/entity-candidates[?q=公司名]`：Companies House 主体候选，只读，不改主体状态；需 `BEACON_COMPANIES_HOUSE_API_KEY`（live 应用下的 REST key；未配置 503，密钥被拒或接口不可用 502）。不传 `q` 时三路合并，按可靠性排序：
   - **官网披露**：抓官网首页和同站的隐私/条款/关于/联系页（至多 5 页），用规则找公司编号和 “… Ltd/Limited” 名称，再按编号精确查。页面里也可能是建站公司等第三方，命中不等于主体。
   - **注册邮编**：查注册邮编与门店相同、SIC 为餐饮类（56 开头）的在营公司；门牌号也对得上的标「门牌一致」。同一邮编常有多家，同一地址也可能先后注册过几家公司。
   - **店名检索**：按店名模糊检索，噪音最多（店名常与公司名不同，结果总会填满 10 条）。
   - 传 `q` 时只按人工输入的公司名检索。
   工作台线索详情页「查 Companies House」打开候选表：默认只显示依据较强的候选（官网披露；同邮编且门牌号或名称对得上，同邮编不超过 3 家时全部显示；仅凭店名的须在营、名称相似且 SIC 不是已知的非餐饮），其余用「显示全部」展开。「采用」只把登记事实和依据填入主体证据并把主体选为 company，核对后点「保存」才生效。
   无官网或查不到时的人工步骤：卖酒的餐厅可查地方议会的场所许可登记（premises licence register），持证人通常就是经营主体；查到后用该公司名检索并把来源写进主体证据。仍查不到就保持 unknown：未查到不等于个体经营，unknown 不放行邮件，电话需同时核对 TPS 与 CTPS。
5. `GET /api/leads/{id}/contact-candidates`：联系方式候选，只读。来源两路：抓官网首页和同站的联系/关于/订位/法律页（至多 5 页），从链接和正文里找邮箱、电话、WhatsApp 链接、社媒账号（Instagram、Facebook、TikTok、X、LinkedIn、YouTube）和带留言框的联系页；以及批次做 Overture 补全时已存下的电话与社媒。同一联系方式两路都有时合并为一条并保留两个来源。分享按钮、单条帖子、模板占位邮箱等不算。
   `POST /api/leads/{id}/contacts` `{items:[{channel, contact_ref, contact_source}]}`：把人工勾选的候选记为渠道准入行，可用性与准入都是 unknown；已存在的（包括已审核过的）跳过，不覆盖。
   工作台线索详情页「联系方式」卡片列出已记录的联系方式；「查找联系方式」打开候选表，默认勾选未记录的，点「记录所选」入库。候选带提示：可能是个人邮箱（免费邮箱域名或前缀不是 info/bookings 之类的职能词）、手机号、已在抑制名单。页面里可能有建站公司、订位平台或连锁其他分店的联系方式，Overture 匹配到的也可能是相邻门店，记录前要核对。
   记录不等于允许使用：准入仍在「任务 → 渠道准入」逐条核对（见 7）。邮件看主体类型，主体 unknown 不放行；电话核对 TPS/CTPS；官网挂 WhatsApp 链接不是营销 opt-in；Instagram、Facebook、TikTok 等社媒与联系表单当前只记录账号，暂缓触达。

研究脚本（抽样、抓取、探针）见 `plan/exploration.md` 六。

## 4 菜单文件

- `POST /api/leads/{id}/assets` `{url}`：按人工核对过的 URL 抓取。阻断本机/内网地址、非 http(s)、非常规端口（解析器映射到代理地址的环境见 `.env.example` 的 `BEACON_FETCH_IP_CHECK`）；重定向逐跳检查；超过 `BEACON_MAX_ASSET_BYTES`（默认 20MB）或超时记为失败并保留原因。`POST /api/assets/{id}/retry` 重试。
- `POST /api/leads/{id}/assets/upload`（multipart `file`）：手工上传 PDF/图片/HTML（按魔数识别）。
- 文件存于 `BEACON_DATA_DIR/evidence/<lead_id>/`，通过 `GET /api/files/<相对路径>` 受控下载。

## 5 分析与审核

- `POST /api/assets/{id}/analyses`（`engine=rules` 默认）：规则引擎提取“菜名 + 价格”（PDF 按坐标分栏）、测量页面/字号/手机等效字号、生成问题候选（`price_format_mixed_decimals`、`price_format_mixed_symbol`、`mobile_text_small`、`pdf_no_text`、`image_only_menu`）。每条都带证据位置。图片与无文本 PDF 进入 `needs_review`。同输入同引擎已有结果时直接返回，不重复创建；`force=true` 强制新版本。
- `engine=provider`：调用配置的模型 provider。`BEACON_LLM_PROVIDER=fake`（默认）不产生任何事实；`deepseek`（`deepseek-flash`，已真实评测：图片转录价格准确率约 98%，观察精确率约一半，每份约 0.004 美元）或 `anthropic`（未真实验证）。图片与图片 PDF 走视觉（PDF 先转前 4 页页图），文本 PDF/HTML 走文本；返回菜品、价格和带位置的观察，一律 `needs_review`，人工核对后才算事实。文本路径会把换行/乱码当排版问题，建议 HTML 与文本 PDF 用规则引擎，模型只用于图片。无密钥返回 503。工作台在文件行有“模型转录”按钮。
- 工作台的“人工新增”页签可在未审核版本上新增问题（必须填位置），用于图片菜单人工目视；新增问题记为人工确认。
- `GET /api/analyses/{id}/evidence`：原文件链接 + 带位置的条目与问题，同屏核对。
- `PATCH /api/analyses/{id}` `{corrections:[{field_path, new_value, reason}]}`：只能改最新版本；生成新版本（`engine=human`，`parent_version`），原版本保留；可改 `items[i].name/price_text/deleted`、`issues[i].confirmed/note/fact/fact_zh/deleted`。确认问题（`confirmed=true`）必须有证据位置。图片或无文本菜单由人转录：`field_path="issues[new]"`（`new_value` 含 `issue_code, fact, evidence, severity`）、`"items[new]"`（`name, price_text, evidence`），记为人工确认。
- HTML 页面正文没有菜单时，分析会给出 `menu_not_in_html` 问题，其 `evidence.pdf_links` / `image_candidates` 是候选文件链接，可复制到“抓取”接入；注意图片候选可能是菜品照片，需人工判断。
- `POST /api/analyses/{id}/review`：完成审核。无问题也可完成。之后才能生成对外内容。

## 6 样稿与文案

- `POST /api/leads/{id}/content` `{kind: sample_partial, analysis_id, section, item_indexes}`：用 `templates/partial_menu.html` 生成一个分区的手机宽度样稿（HTML；本机有 Chrome 时同时出 PNG）。菜名与价格原样填入。
- `{kind: message_short, analysis_id, sender_identity, opt_out_text, website}`：短文案只引用已确认问题的事实；必须含发送身份与退出方式；含未经证据的表述（到店、案例、过敏原、素食、利润等）会被拒绝。
- `POST /api/content/{id}/revise` `{body_text}`：编辑生成新版本草稿（同样校验）。
- `POST /api/content/{id}/approve` `{decision: approved|rejected, note}`：审批绑定当前内容 hash 与源分析 hash。内容编辑、出现更新版本、源分析修正都会使审批失效（`approval_valid=false`，附原因），需重新生成/审批。

## 7 渠道准入与人工任务

- `POST /api/leads/{id}/eligibility`：每个渠道 + 联系值一条；`contact_usable`（unknown/valid/invalid）与 `eligibility`（unknown/allowed/blocked）分开记录。`allowed` 必须填 `rule_version` 与 `evidence`（如 ICO B2B 指引、TPS/CTPS 筛查结果、opt-in 记录）；系统记录审核人与时间；可设 `review_due_at`。模型不能改准入。
- `POST /api/leads/{id}/tasks` `{eligibility_id, content_id}`：创建前复核准入 allowed、联系可用、审批有效、未抑制、复核未到期；任一不满足返回 409 及原因。
- `POST /api/tasks/{id}/open`：打开只记录打开（再次复核）。
- `POST /api/tasks/{id}/sent` `{sent_at, notes}`：销售人工发送后回填，记录操作者与实际时间；系统不调用发送接口。复核失败会把任务置为 `paused` 并给出原因。
- `POST /api/tasks/{id}/cancel|resume`：取消 / 暂停后由负责人明确恢复。

## 8 回复、拒收与抑制

`POST /api/leads/{id}/events` `{event_key, kind, channel, occurred_at, payload}`：`event_key` 幂等（重复提交返回 `duplicate=true`，不重复执行）。
- `reply`：暂停该线索所有未完成任务，等负责人决定；`payload.intent` 可填 positive / quote / later / no / unknown，用于统计。
- `reject` / `unsubscribe`：写入抑制（门店范围；`payload.contact_ref` 另写联系值范围），取消所有未完成任务；即使没有任务也保存。
- `bounce`：该渠道/联系值标记无效，取消对应任务。
`GET /api/suppressions` 查看抑制名单。

## 9 成本、汇总与导出

- `POST /api/costs`：`category` = setup / processing / outreach；金额需币种；或只填分钟数。
- `GET /api/batches/{key}/summary`：N/M/I/E/S/R/P/Q 按门店去重，比率带分子分母，分母为零写“不适用”；分渠道单列；单位成本只在单一币种且分母非零时计算；`commercial_status` 在无实际触达时为“未验证”。
- `GET /api/batches/{key}/export.csv`：逐店状态。

## 10 批量处理与续跑

`POST /api/batches/{key}/runs` `{steps:[fetch, analyze], max_jobs}`：为每个待抓取/待分析文件建 job，顺序执行；一条失败不影响其余；已有有效分析的不重做。`POST /api/runs/{id}/resume` 重置失败与超时（30 分钟）仍在运行的 job 后续跑。`GET /api/runs/{id}` 查看每个 job 的状态、尝试次数与错误。

## 11 备份与恢复

```bash
infra/backup.sh "$BEACON_DATA_DIR" backups      # pg_dump 自定义格式 + 数据目录 tar，输出 sha256
infra/restore.sh backups/beacon-<ts>.dump beacon_restore_drill backups/data-<ts>.tgz /tmp/restore
```

恢复演练记录见 `plan/exploration.md`“D10 演练”。生产恢复时把目标库名换成 `beacon` 并停止 API。

数据库与文件目录必须一起迁移。记录里的 `file_path` 指向数据目录内的文件；只恢复数据库不恢复文件时，分析会报 `FileNotFoundError` 并写成 `failed`（重试即可）。把本机数据目录搬进容器卷：

```bash
docker cp "$BEACON_DATA_DIR/." beacon-api:/data/
```

切换模型 provider：在 `infra/.env` 写 `BEACON_LLM_PROVIDER=deepseek` 与 `BEACON_DEEPSEEK_API_KEY=…`，然后 `docker compose -f infra/docker-compose.yml up -d api` 重建 api 容器（`restart` 不会重新读取 env 文件）。已在容器内用一份真实图片菜单验证通过（26 条菜品、4 条观察，约 3000 输出 token）。

## 12 已知限制

- DeepSeek provider 已真实评测（见 `plan/model-eval-v1.md`），转录仍需逐项核对；Anthropic provider 未经真实验证。
- 规则提取覆盖“名称 + 价格”行，多价（大/小份）与描述行需人工补。
- 批量运行为同步执行，适合 ≤100 家；更大批次再引入 Celery。
- 访问控制为单操作者会话，未做角色区分；网络部署前需加 HTTPS 与访问限制。
- 保留期与匿名化任务未实现（记录字段已具备 `collected_at`）。
