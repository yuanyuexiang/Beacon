# Beacon 最小工具操作手册（v0.1，2026-09-30）

面向单操作者试点。所有业务接口在 `/api` 下且需登录；`/api/docs` 为交互式接口文档（FastAPI 自带）。系统不发送任何消息，所有对外联系由人执行后回填。

## 1 启动

方式一：Docker 一键全套（推荐用于试运行和测试）

```bash
cp infra/.env.example infra/.env        # 填 BEACON_SECRET_KEY、引导账号、模型密钥（可选）
docker compose -f infra/docker-compose.yml up -d --build
```

起来后：工作台 http://localhost:3000，接口文档 http://localhost:8000/api/docs。api 容器启动时自动执行迁移；数据文件在卷 `beacon-data`，数据库在卷 `beacon-pgdata`。容器内没有 Chrome，样稿只生成 HTML（本机运行时才出 PNG）。在容器里跑后端测试：

```bash
docker compose -f infra/docker-compose.yml --profile test run --rm api-test
```

方式二：本机开发（只用 Docker 起数据库）

```bash
docker compose -f infra/docker-compose.yml up -d postgres   # PostgreSQL 16，端口 5433
cp apps/api/.env.example apps/api/.env                       # 填写 BEACON_DATA_DIR（绝对路径）、BEACON_SECRET_KEY、引导账号
cd apps/api && uv sync && uv run alembic upgrade head
uv run uvicorn app.main:app --reload --port 8000
pnpm install && pnpm --filter beacon-web dev                 # 另一个终端，http://localhost:3000
```

首次启动时若无操作者，用 `.env` 中的 `BEACON_BOOTSTRAP_OPERATOR/PASSWORD` 创建首个操作者；之后修改 `.env` 不会再创建。

## 2 登录

`POST /api/auth/login` `{username, password}` → 设置 HttpOnly 会话 cookie（12 小时）。`GET /api/auth/me` 查看当前操作者，`POST /api/auth/logout` 退出。

## 3 批次与名单

推荐在工作台按「门店池 → 添加关注地区／立即同步 → 建立销售名单」使用。FSA 同步先更新独立的来源池；「建立名单」与「追加商户」只读本地池，不等待 FSA。来源更新不自动改变已有名单成员、人工官网、联系方式或跟进记录。CSV 与空名单仍可使用；历史研究同步接口保留，历史未完成的 FSA 任务按原参数恢复。详见文末 D57。


1. `POST /api/batches`：`batch_key`、`country`（如 GB）、`region`、`source_name`（如 fsa）、`source_version`（FSA extractDate）、`source_licence`（OGL-3.0）、`sampling_method`、`sampling_seed`。 工作台「建立名单」默认自动获取：填写地区、商户类型与名单名称，获取所选类型的全部商户；客户界面不设置数量或随机抽样。创建后依次执行门店池选入、Overture、预筛与联系方式，在统一任务面板显示进度。D54 将参数和进度保存至数据库：失败点击「重试未完成步骤」，刷新后点击「查看 / 继续任务」，成功步骤不重做。关闭面板但保留本页时继续执行；离开或刷新后，当前请求的结果可能已保存，后续步骤需要点击继续，不承诺浏览器关闭后全流程后台运行。
   创建方式也支持「导入 CSV」（选文件后创建并导入）和「仅建空名单」。CSV 行错误在结果中显示计数，修正后通过「追加 CSV」导入当前名单。来源与许可按创建方式记录；CSV 不自动标注 FSA 许可。
   D55 客户名单采用全量获取，不生成随机种子；原研究接口和历史任务保留已有抽样参数，用于复现旧记录。默认保留 FSA 尚未首次检查的商家，在列表显示「待首次检查」标签；此状态不代表已确认新开业或可联系。在高级选项／高级筛选里可选择排除，历史批次不重算。
   `DELETE /api/batches/{key}?confirm={key}`：删除批次，不可恢复，处理过的批次也能删。只属于该批次的门店连同菜单文件、分析、样稿文案、联系方式与准入、任务、回复事件一并删除，受控目录里的证据与样稿文件也删除；批次的导入、运行和成本记录一并删除。两类门店保留：同时属于其他批次的；有拒收/退订抑制记录的（脱离批次但保留，日后重新导入同一名录会关联回原门店，抑制继续生效）。`GET /api/batches/{key}/delete-preview` 先看影响范围。工作台「删除批次」会列出将删除与保留的数量，需输入批次键确认。删除写入审计日志；验证报告引用过的批次删除后无法在系统内复核其分子分母。
2. `POST /api/imports`（multipart：`batch_key`、`file`）：CSV 需含 `name` 和 `fhrsid` / `source_key`(`fsa:416314`) / `source_id` 之一；可选 `address, postcode, lat, lng, website, sample_order, screening_class, screening_reason`。返回逐行错误；同批次重导不新增；已存在门店跨批次关联；不按店名合并。
3. `GET /api/leads?batch_key=`、`PATCH /api/leads/{id}`（官网、筛选分类与原因、法律主体状态与证据；主体默认 unknown）。
4. `GET /api/leads/{id}/entity-candidates[?q=公司名]`：Companies House 主体候选，只读，不改主体状态；需 `BEACON_COMPANIES_HOUSE_API_KEY`（live 应用下的 REST key；未配置 503，密钥被拒或接口不可用 502）。不传 `q` 时三路合并，按可靠性排序：
   - **官网披露**：抓官网首页和同站的隐私/条款/关于/联系页（至多 5 页），用规则找公司编号和 “… Ltd/Limited” 名称，再按编号精确查。页面里也可能是建站公司等第三方，命中不等于主体。
   - **注册邮编**：查注册邮编与门店相同、SIC 为餐饮类（56 开头）的在营公司；门牌号也对得上的标「门牌一致」。同一邮编常有多家，同一地址也可能先后注册过几家公司。
   - **店名检索**：按店名模糊检索，噪音最多（店名常与公司名不同，结果总会填满 10 条）。
   - 传 `q` 时只按人工输入的公司名检索。
   工作台线索详情页「查 Companies House」打开候选表：默认只显示依据较强的候选（官网披露；同邮编且门牌号或名称对得上，同邮编不超过 3 家时全部显示；仅凭店名的须在营、名称相似且 SIC 不是已知的非餐饮），其余用「显示全部」展开。「采用」只把登记事实和依据填入主体证据并把主体选为 company，核对后点「保存」才生效。
   无官网或查不到时的人工步骤：卖酒的餐厅可查地方议会的场所许可登记（premises licence register），持证人通常就是经营主体；查到后用该公司名检索并把来源写进主体证据。仍查不到就保持 unknown：未查到不等于个体经营，unknown 不放行邮件，电话需同时核对 TPS 与 CTPS。
5. `GET /api/leads/{id}/contact-candidates`：联系方式候选，只读。来源两路：抓官网首页和同站的联系/关于/订位/法律页（至多 5 页），从链接和正文里找邮箱、电话、WhatsApp 链接、社媒账号（Instagram、Facebook、TikTok、X、LinkedIn、YouTube）和带留言框的联系页；以及批次做 Overture 补全时已存下的电话与社媒。同一联系方式两路都有时合并为一条并保留两个来源。分享按钮、单条帖子、模板占位邮箱等不算。
   `POST /api/leads/{id}/contacts` `{items:[{channel, contact_ref, contact_source}]}`：把人工勾选的候选记为渠道准入行，可用性与准入都是 unknown；已存在的（包括已审核过的）跳过，不覆盖。
   工作台线索详情页「联系方式」卡片列出已记录的联系方式；「查找联系方式」调用 `POST /api/leads/{id}/contact-review`，基于页面上下文进行 AI 筛选，默认仅展示并勾选未记录且未抑制的优先推荐项，点「记录所选」入库；其余通过“查看全部候选”展开。候选带提示：可能是个人邮箱（免费邮箱域名或前缀不是 info/bookings 之类的职能词）、手机号、已在抑制名单。页面里可能有建站公司、订位平台或连锁其他分店的联系方式，Overture 匹配到的也可能是相邻门店，记录前要核对。
   批量查找：`POST /api/batches/{key}/runs` `{steps:["contacts"], max_jobs:20}`，之后反复 `POST /api/runs/{id}/continue` `{max_jobs:20}` 直到没有待处理的 job。每一块里的官网并行读取（最多 8 个站点同时进行；同一主机的多个地址排队，不对单个站点并发加压），数据库写入仍逐家进行（`continue` 不重置失败的 job，重试失败用 `resume`）。对象是未被筛选排除、有官网或 Overture 数据的门店；只自动记录经过证据校验的 AI 优先推荐项（仍是 unknown/unknown，已有的不覆盖，在抑制名单里的不记）。备选、不推荐和证据不足项保留；不再按候选数量、邮箱前缀或 Overture 重复命中直接自动记录。AI 未配置或失败时不新增自动记录。每家的查找摘要写在 `lead.raw.contacts_scan`，同一个官网成功查过且已完成本版 AI 筛选后不重复查；旧版本、官网更换、页面读取失败，或真实 AI 配置后上次判断未完成时可在新补充任务重查。工作台在「建立名单」「完善名单」「追加商户」的统一流水线中调用，持久化同一运行 ID；任务内失败重试只处理失败或中断的 job，线索列表的「联系方式」列显示已记录的数量。
   记录不等于允许使用：准入仍在「任务 → 渠道准入」逐条核对（见 7）。邮件看主体类型，主体 unknown 不放行；电话核对 TPS/CTPS；官网挂 WhatsApp 链接不是营销 opt-in；Instagram、Facebook、TikTok 等社媒与联系表单当前只记录账号，暂缓触达。

### 搜索补官网（Exa，单家人工确认）

在线索列表点「搜索补官网」，或在详情页「基本信息与人工判断」点「搜索官网候选」。打开窗口只读取上次候选，点击「搜索」才发起外部查询，默认搜索词包含店名、地址和邮编，可手工调整。

- `GET /api/leads/{id}/website-search`：最近一次候选；`POST` 同一路径 `{query?: string}`：检索最多 5 个页面，保存查询词、时间、页面 URL 和至多 1500 字的搜索摘录。不自动修改官网或准入。
- 搜索摘录不是实时抓取证据；邮编出现只作提示。目录、社媒和疑似演示站带提示，但提示规则并不能识别所有错误页面。打开原页面核对门店地址、经营者和页面真实性。
- 点「核对并确认」，勾选地址与商家运营核对，填写核对依据，再「确认并保存官网」。确认记录包含来源、查询词、搜索时间、审核人、审核时间及依据；记录审计。已有官网会提示替换；确认前官网已被其他操作修改时返回 409，刷新后再核对。
- `POST /api/leads/{id}/website-confirm`：`search_id, candidate_id, expected_website, address_checked, official_checked, evidence`。服务端只接受当前搜索中的候选，超过七天须重新搜索。
- 搜索缓存只保留最近一轮候选，不复制完整上游响应。七天是候选确认有效期，不是数据删除期限；候选随门店记录清理。人工确认的来源与依据保留供追溯。
- 未配置 `BEACON_EXA_API_KEY` 时使用免费限流服务；可在 `infra/.env`（Docker）或 `apps/api/.env`（本机）配置可选密钥，重新启动 API 生效。限流返回 429，拒绝访问 503，超时 504，异常响应 502；失败不覆盖上次候选，不自动重试。
- 确认后可按现有流程查找联系方式和接入菜单，渠道准入仍须单独审核。未接入 Jina 或社媒登录态抓取。

Exa 官方接入说明：[Exa MCP](https://exa.ai/docs/get-started/exa-mcp)。

研究脚本（抽样、抓取、探针）见 `plan/exploration.md` 六。

## 4 菜单文件

- `POST /api/leads/{id}/assets` `{url}`：按人工核对过的 URL 抓取。阻断本机/内网地址、非 http(s)、非常规端口（解析器映射到代理地址的环境见 `.env.example` 的 `BEACON_FETCH_IP_CHECK`）；重定向逐跳检查；超过 `BEACON_MAX_ASSET_BYTES`（默认 20MB）或超时记为失败并保留原因。`POST /api/assets/{id}/retry` 重试。
- `POST /api/leads/{id}/assets/upload`（multipart `file`）：手工上传 PDF/图片/HTML（按魔数识别）。
- 文件存于 `BEACON_DATA_DIR/evidence/<lead_id>/`，通过 `GET /api/files/<相对路径>` 受控下载。

## 5 分析与审核

- `POST /api/assets/{id}/analyses`（`engine=rules` 默认）：规则引擎提取“菜名 + 价格”（PDF 按坐标分栏）、测量页面/字号/手机等效字号、生成问题候选（`price_format_mixed_decimals`、`price_format_mixed_symbol`、`mobile_text_small`、`pdf_no_text`、`image_only_menu`）。每条都带证据位置。图片与无文本 PDF 进入 `needs_review`。同输入同引擎已有结果时直接返回，不重复创建；`force=true` 强制新版本。
- `engine=provider`：调用配置的模型 provider。`BEACON_LLM_PROVIDER=fake`（默认）不产生任何事实；`deepseek`（`deepseek-flash`，已真实评测：图片转录价格准确率约 98%，观察精确率约一半，每份约 0.004 美元）或 `anthropic`（未真实验证）。图片与图片 PDF 走视觉（PDF 先转前 4 页页图），文本 PDF/HTML 走文本；返回菜品、价格和带位置的观察，一律 `needs_review`，人工核对后才算事实。文本路径会把换行/乱码当排版问题，建议 HTML 与文本 PDF 用规则引擎，模型只用于图片。无密钥返回 503。工作台在文件行有“模型转录”按钮。
- 工作台的“人工新增”页签可在未审核版本上新增问题（必须填位置），用于图片菜单人工目视；新增问题记为人工确认。
- `GET /api/analyses/{id}/evidence`：原文件链接 + 带位置的条目与问题，同屏核对。
- `PATCH /api/analyses/{id}` `{corrections:[{field_path, new_value, reason}]}`：只能改最新版本；生成新版本（`engine=human`，`parent_version`），原版本保留；可改 `items[i].name/price_text/deleted`、`issues[i].confirmed/note/fact/fact_zh/deleted`。确认问题（`confirmed=true`）必须有证据位置。图片或无文本菜单由人转录：`field_path="issues[new]"`（`new_value` 含 `issue_code, fact, evidence, severity`）、`"items[new]"`（`name, price_text, evidence`），记为人工确认。
- HTML 页面正文没有菜单时，分析会给出 `menu_not_in_html` 问题，其 `evidence.pdf_links` / `image_candidates` 是候选文件链接，可复制到“抓取”接入；注意图片候选可能是菜品照片，需人工判断。
- `POST /api/analyses/{id}/review`：完成审核。无问题也可完成。之后才能生成对外内容。

## 6 样稿与文案

- `POST /api/leads/{id}/content` `{kind: sample_partial, analysis_id, section, item_indexes}`：用 `templates/partial_menu.html` 生成一个分区的手机宽度样稿（HTML；本机有 Chrome 时同时出 PNG）。菜名与价格原样填入。
- `{kind: message_short, analysis_id, sender_identity, opt_out_text, website}`：短文案只引用已确认问题的事实；必须含发送身份与退出方式；含未经证据的表述（到店、案例、过敏原、素食、利润等）会被拒绝。
- `POST /api/content/{id}/revise` `{body_text}`：编辑生成新版本草稿（同样校验）。
- `POST /api/content/{id}/approve` `{decision: approved|rejected, note}`：审批绑定当前内容 hash 与源分析 hash。内容编辑、出现更新版本、源分析修正都会使审批失效（`approval_valid=false`，附原因），需重新生成/审批。

## 7 渠道准入与人工任务

- `POST /api/leads/{id}/eligibility`：每个渠道 + 联系值一条；`contact_usable`（unknown/valid/invalid）与 `eligibility`（unknown/allowed/blocked）分开记录。`allowed` 必须填 `rule_version` 与 `evidence`（如 ICO B2B 指引、TPS/CTPS 筛查结果、opt-in 记录）；系统记录审核人与时间；可设 `review_due_at`。模型不能改准入。
- `POST /api/leads/{id}/tasks` `{eligibility_id, content_id}`：创建前复核准入 allowed、联系可用、审批有效、未抑制、复核未到期；任一不满足返回 409 及原因。
- `POST /api/tasks/{id}/open`：打开只记录打开（再次复核）。
- `POST /api/tasks/{id}/sent` `{sent_at, notes}`：销售人工发送后回填，记录操作者与实际时间；系统不调用发送接口。复核失败会把任务置为 `paused` 并给出原因。
- `POST /api/tasks/{id}/cancel|resume`：取消 / 暂停后由负责人明确恢复。

## 8 回复、拒收与抑制

`POST /api/leads/{id}/events` `{event_key, kind, channel, occurred_at, payload}`：`event_key` 幂等（重复提交返回 `duplicate=true`，不重复执行）。
- `reply`：暂停该线索所有未完成任务，等负责人决定；`payload.intent` 可填 positive / quote / later / no / unknown，用于统计。
- `reject` / `unsubscribe`：写入抑制（门店范围；`payload.contact_ref` 另写联系值范围），取消所有未完成任务；即使没有任务也保存。
- `bounce`：该渠道/联系值标记无效，取消对应任务。
`GET /api/suppressions` 查看抑制名单。

## 9 成本、汇总与导出

- `POST /api/costs`：`category` = setup / processing / outreach；金额需币种；或只填分钟数。
- `GET /api/batches/{key}/summary`：N/M/I/E/S/R/P/Q 按门店去重，比率带分子分母，分母为零写“不适用”；分渠道单列；单位成本只在单一币种且分母非零时计算；`commercial_status` 在无实际触达时为“未验证”。
- `GET /api/batches/{key}/export.csv`：逐店状态。

## 10 批量处理与续跑

`POST /api/batches/{key}/runs` `{steps:[fetch, analyze], max_jobs}`：为每个待抓取/待分析文件建 job，顺序执行；一条失败不影响其余；已有有效分析的不重做。`POST /api/runs/{id}/resume` 重置失败与超时（30 分钟）仍在运行的 job 后续跑。`GET /api/runs/{id}` 查看每个 job 的状态、尝试次数与错误。

## 11 备份与恢复

```bash
infra/backup.sh "$BEACON_DATA_DIR" backups      # pg_dump 自定义格式 + 数据目录 tar，输出 sha256
infra/restore.sh backups/beacon-<ts>.dump beacon_restore_drill backups/data-<ts>.tgz /tmp/restore
```

## AI 自动补全官网与菜单（D45）

## Google Maps 菜单获取（D46）

入口：线索详情 → **菜单文件** → **从 Google Maps 获取菜单** → **开始获取菜单**。需要门店地址和邮编；已关联 Google Place ID 时优先使用该 ID，否则通过名称、地址搜索并校验页面。任务进度显示在弹窗，关闭弹窗不会取消任务；结束后菜单文件和分析自动刷新。

专用浏览器自动进入菜单页签，只处理菜单图片区的前 5 张（每张最多 15 MB），打开查看器下载资源。服务端再次核对名称、街道/门牌号和邮编、来源与任务版本，去重复用；菜单拍摄/有效日期没有证据则为未知。有真实 DeepSeek 配置时，新文件自动转录，名称价格和问题仍待审核；已有文件的审核不覆盖。菜单缺失、有限视图、验证码、超时、资料改变和执行器离线均明确报告，不当成获取成功。执行器中断超过 15 分钟后可重试；已入库图片保留。

本机配置（仓库根目录；已配置的机器无需重复生成）：

```bash
python3 scripts/configure_maps_worker.py
docker compose -f infra/docker-compose.yml up -d --build api web
uv run --project apps/api --extra maps-worker python scripts/maps_menu_worker.py --token-file data/browser-profiles/maps-worker.token
```

生成独立随机密钥写入受控 token 文件与已忽略的 apps/api/.env、infra/.env，不显示密钥；重建 API 后生效。执行器默认连接 http://127.0.0.1:8000，复用 data/browser-profiles/maps-menu-test，代理为 socks5h://127.0.0.1:7890，不改系统代理。需要已安装 Google Chrome。保持执行器运行即可在工作台点击按钮，Ctrl+C 停止；电脑重启后重新运行执行器。不要同时启动使用同一 profile 的登录探针或其他浏览器。

可用参数：`--api-base`（远程必须 HTTPS）、`--profile`（专用目录）、`--proxy`（空串直连）、`--headless`（研究用，可能有限视图）、`--once`（一项任务后退出）。执行器主动连接 API，无需向外暴露 Chrome 调试端口；token 与 profile 都是敏感受控资料，不提交 Git。API 地址更改后需匹配目标 API 的执行器密钥。服务器需要独立持久化 profile、Chrome 与有界面环境；当前没有验证全新服务器成功率，不可把本机成功等同服务器部署已完成。

Maps 弹窗显示原线索和本次 Maps 的名称、地址、官网与观测时间，并显示历史来源记录。已关联 Place ID 的门店直接获取菜单，来源差异不阻止导入，也不覆盖原线索。未关联的搜索仍核对门店；旧失败任务可以重新获取。

### 使用顺序

1. 打开「门店池」。已有 FSA 名单关注的地区会自动登记，但旧抽样名单不会被当作完整池；初次仍需同步。

### 数据与失败恢复

来源池与 Lead 分开。池内当前记录按 FHRSID 去重，保存原始 FSA 响应、归一化字段、首次／最近确认时间与来源版本；每次请求范围在排队时固定。完整读取全部所选类型并核对分页、来源 ID、地区／类型后，再一次性更新池；失败回滚池的变更，成功快照仍可使用。重复点击同步不会建立重复活动任务；worker 重启会恢复未完成运行，多个 worker 只有一个执行者。

## 客户工作流程与菜单四步（D63）

名单、准备抽屉与沟通页显示四个工作区域：完善客户资料、准备触达、确认发送、沟通跟进。它们表示所在工作区域，不代表之前所有资料已补齐。创建任务后才进入沟通页的范围保持不变。

线索详情的菜单步骤调整为：

1. 获取菜单：可从官网／单家 Maps 获取、填入已核对 URL 或上传；直接 URL“获取并分析”和“上传并分析”会自动接续分析，获取或分析失败分别保留结果。联系方式提前展示，与菜单并行完善；暂时没有菜单可保存准备草稿，不会卡住名单。
2. AI 分析：点击“开始分析”，自动判断可读文字或图片。文本 PDF／HTML 直接提取，图片／扫描件需要真实 AI；缺少配置时保留文件并提示，不用 Fake 生成实际结果。已有同输入结果会复用。
3. 核对事实：对照原文件核对菜名、价格及问题，仅确认有依据的问题，然后完成事实核对。模型分析仍待核对；失败、等待、运行中的分析不能完成核对。最新版本未核对或失败时不能靠旧审批推进；另一份可用菜单不受无关失败文件阻塞。
4. 准备触达：打开共用抽屉，选择渠道与联系人，核对准入、身份和退出说明，生成文案并明确审批当前版本。缺项可保存草稿；创建就绪任务不会发送消息，到沟通页继续预览确认。

前端进度只按最新有效菜单分析计算，不依据样稿存在、文案审批或“随便有一条分析”推高菜单进度。没有已核实菜单事实时不能引用菜单问题，渠道准入和发送前检查仍由后端执行。

## 销售总监与门店分配（D70）

管理员在“用户管理”创建账号或编辑角色，选择“销售总监”。该角色可以查看和操作全量业务门店、管理名单、分配／转交门店及查看团队工作量；不能管理账号、角色、系统密钥、Gmail／社媒凭据及管理员设置。创建用户仍由管理员负责。只读成员保留全量只读，不能分配、修改或发送。

批次与线索增加“全部门店／我的门店／未分配”和负责人筛选。总监或管理员勾选门店后点“分配门店”；未勾选时不默认分配全名单；需在弹窗明确选择“当前筛选全部”，包含其他分页。预览显示数量与原负责人分组，选择有效业务成员、填写原因后确认；也可“收回为未分配”。单次最多 5000 家。每家返回成功、未变化或失败原因；若预览后被别人转交，会拒绝覆盖，请重新预览。详情页顶部也支持单家分配及查看分配记录。

一家门店只有一个当前负责人，跨批次共用，不因重复选入名单产生第二份归属。旧门店升级后保留未分配，不根据旧任务擅自推断归属。业务成员默认只显示自己的门店；尚未分配时列表为空，由总监分配。成员可在自己门店补资料、分析、准备触达和跟进，但不能建删名单、操作整批流水线、导入原始门店、转交门店或代派任务。总监在分配窗口可查看各成员门店数、未完成任务、准备草稿、到期待跟进和最近沟通时间；不生成主观业绩评分。

业务成员的门店、菜单、分析、文件、文案、任务、会话、发送记录、统计和导出均按当前门店归属过滤；后端同时检查写入，不只隐藏按钮。成员只能把任务留给自己；管理者为其他成员准备任务时，须先分配该门店。新草稿／任务默认继承门店负责人，未分配时管理者沿用当前操作者。后台发送再次核查负责人是否仍有权限、账号是否有效。

交接时，未完成草稿和任务的负责人随门店更新，跟进提醒保留，未完成任务暂停，待发预览及排队记录撤销且清除旧确认令牌。新负责人须复核并恢复任务、重新生成最终发送预览。发送中或结果未知的门店拒绝交接，先完成对账。已完成任务、原执行人、邮件及回复历史不改写；分配人、时间、原／新负责人和原因写入审计。转交、停用或恢复账号均不会自动发送消息。离职交接先筛选原负责人转交，再停用账号；已停用成员的门店仍可由总监收回或转交。

## 单家门店继续完善与重新完善（2026-10-25）

批量处理之后，进入门店详情，顶部“门店资料”显示四项资料状态。打开详情只读取已存结果，不自动产生查询或模型调用。

1. **继续完善**：打开抽屉，默认选择缺失、失败或过期项目；可取消不需要的项目，再点“开始完善所选项”。
2. **重新完善**：主动更新选中的资料；人工确认官网保留，不同候选在研究／来源记录中核对。重新分析会创建新版本，需要重新核对相关事实和文案。
3. **单项处理**：每项显示最近处理时间及失败原因，可“更新此项”或“重试此项”。菜单项可跳转查看或上传菜单。
4. **任务进度**：任务在后台执行，刷新或离开页面不会取消。已有批量任务包含这家门店时，显示该任务进度，不另起一份；批量任务仍在名单页管理。
5. **结束任务**：单家任务可在抽屉结束，已获得结果保留。当前外部请求可能仍完成，但不会继续下一项。

菜单获取复用单家 AI 研究并自动分析新菜单，成功的相同内容分析不重做；选择“菜单 AI 分析”重新完善才主动生成新版本。不自动抓取 Maps，没有菜单仍可直接准备询问菜单或负责人的消息。

管理员、销售总监可操作有权限的门店；业务成员仅操作已分配门店，后台执行前再次核验归属；只读用户可查看状态。
