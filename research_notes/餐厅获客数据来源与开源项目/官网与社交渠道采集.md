# 从"餐厅名 + 官网/地点"补全联系渠道与菜单（欧洲，截至 2026-09）

> 范围：给定一家餐厅（名称 + 官网或 place），补全 电话 / WhatsApp / Instagram / Facebook / 邮箱 / 联系表单 URL / 负责人姓名 / 当前菜单。
> 与前一份笔记《欧洲餐厅菜单获客系统可行性/数据来源.md》不重复：Google Places 字段与条款、OSM 覆盖率、Foursquare/Yelp/Outscraper 定价、德国 §5 DDG、邮箱验证价格等见该文件。

## 1. 各渠道在欧洲餐厅官网上的位置：JSON-LD、页脚、Impressum / mentions légales / aviso legal

### Takeaway
结构化数据（schema.org JSON-LD）是"便宜但覆盖低"的第一层：全网 41% 的页面有 JSON-LD，但只有约 0.19% 的移动页面标注了 Restaurant 类型、3.97% 标注了 LocalBusiness；WDC 2024 语料中只有 84,256 个主机含 Restaurant 实体。多数渠道仍须从页脚链接、联系页和法定信息页（DE/AT Impressum、FR mentions légales、ES aviso legal）里解析。三国法律都要求公开"直接联系方式"，所以这些页面是拿到邮箱和电话最稳的地方，负责人姓名也常写在这里。

### Cited Findings
- Web Almanac 2024：41% 的页面用 JSON-LD（2022 年为 34%），26% 用 Microdata — [Web Almanac 2024 Structured Data](https://almanac.httparchive.org/en/2024/structured-data)
- Web Almanac 2024（移动页面，JSON-LD 类型）：WebSite 12.73%，Organization 7.16%，LocalBusiness 3.97%，**Restaurant 0.19%** — [Web Almanac 2024](https://almanac.httparchive.org/en/2024/structured-data)
- Web Almanac 2024：JSON-LD sameAs 指向 Facebook 的页面占 4.53%，Instagram 3.67%，LinkedIn 1.11% — [Web Almanac 2024](https://almanac.httparchive.org/en/2024/structured-data)
- 历史对比：2022 年 LocalBusiness 在桌面页面占 2.3%、移动页面 2.8%，Restaurant 为 0.3% — [Web Almanac 2022](https://almanac.httparchive.org/en/2022/structured-data)（这是搜索摘要里的数字，本次没有逐字核对原文）
- Web Data Commons 2024-12 schema.org 子集中，**Restaurant 类**有 158,662,564 条 quads、1,186,870 个 URL、**84,256 个主机**；同时出现最多的类为 Offer（6.2M）、**MenuItem（3,963,413）**、Restaurant（2,969,736）。**LocalBusiness 类**有 27,184,047 个 URL、1,456,650 个主机 — [WDC Schema.org Subsets 2024](https://webdatacommons.org/structureddata/2024-12/stats/schema_org_subsets.html)（本次 curl 实测）
- Google 的 LocalBusiness 结构化数据文档说明了支持的属性（telephone、address、openingHours、menu、servesCuisine、priceRange 等）— [Google LocalBusiness Structured Data](https://developers.google.com/search/docs/appearance/structured-data/local-business)（字段清单来自已有知识；本次没有抓取该页面逐项核对）
- 奥地利：§5 ECG 要求用户能"长期、方便、直接"访问联系信息（含邮箱）；§§24/25 MedienG 另外规定媒体的 Impressum 与披露义务；这些义务也适用于新闻通讯和商务邮件 — [WKO Impressum und Offenlegung](https://www.wko.at/information-consulting/werbung-marktkommunikation/impressum-und-offenlegung)；[internet4jurists §5 ECG](https://www.internet4jurists.at/e-commerce/impressum1a.html)
- 法国：mentions légales 依据 LCEN（2004-575 号法律）第 6 条，必须写明出版人身份（姓名/公司名、地址）、法律信息（SIRET/RCS）、托管商联系方式、**出版负责人（directeur de la publication）姓名**，以及一种直接联系方式 — [Légifrance LCEN art. 6](https://www.legifrance.gouv.fr/loda/article_lc/LEGIARTI000044067469)；[Simonnet Avocat](https://www.simonnetavocat.fr/mentions-legales-dun-site-internet-obligations-sanctions-et-modele/)
- 西班牙：LSSI-CE 第 10 条要求"永久、方便、直接、免费"地提供身份信息和联系方式，包括邮箱和其他能直接有效沟通的方式（如电话）— [LSSI FAQ (mineco)](https://lssi.mineco.gob.es/la-ley/Paginas/preguntas-frecuentes.aspx)；[Usercentrics aviso legal](https://usercentrics.com/es/knowledge-hub/aviso-legal-web/)

### Inferences
- 解析优先级建议：① 首页 `<script type="application/ld+json">`（取 telephone / email / sameAs / hasMenu / menu / servesCuisine / priceRange / address）→ ② 页脚与页头的 `tel:` / `mailto:` / `wa.me` / `api.whatsapp.com/send` / instagram.com / facebook.com 链接 → ③ 法定信息页：/impressum /imprint（DE/AT）、/mentions-legales（FR）、/aviso-legal /aviso-legal-y-privacidad（ES）、/note-legali（IT，未查证）→ ④ /contact /kontakt /contacto /contatti，用 `<form>` 判断这是联系表单 URL → ⑤ /privacy /datenschutz（写着数据控制者的姓名和邮箱）。
- 决策人姓名：DE Impressum 的 "Inhaber / Geschäftsführer / Vertretungsberechtigt"、FR 的 "directeur de la publication"、ES aviso legal 里的持有人（titular）一般是法定所有人或经理人，是能公开获取的最好的负责人来源。不过这属于个人数据，处理时要做 GDPR 合法利益评估。
- JSON-LD 覆盖率太低（Restaurant 标注页 <1%），只能作为"命中即高置信"的加分项，不能当主路径。Wix、Squarespace 以及 WordPress 的 Yoast/RankMath 插件常自动输出 LocalBusiness/Organization，Restaurant 子类型较少。这一条是推断，没有找到按建站平台拆分的统计。

### Gaps
- 没有找到"欧洲餐厅官网中带 JSON-LD 的比例"或"带 hasMenu 的比例"这类按行业、按国家的统计；Web Almanac 只有全网比例。
- WDC 按顶级域（.de/.fr/.es/.it）拆分的 Restaurant 主机数没有拿到。
- 意大利 "note legali" 与 P.IVA 公示义务没有检索。

## 2. 餐厅常用建站平台与菜单存放位置（Wix / Squarespace / WordPress / 预订与菜单 SaaS）

### Takeaway
主流建站工具都有原生菜单组件，所以菜单可能以 HTML 文本、PDF 或图片出现：Wix Restaurants Menus 可导入 PDF（最多 100 页）/ 图片 / CSV / Excel，前端输出结构化 HTML；Squarespace 有专门的 Menu block（HTML 文本）。按平台划分的欧洲餐厅份额没有找到可靠数据。

### Cited Findings
- Wix Restaurants Menus 应用可创建多份菜单；导入支持 PNG、JPG、WEBP、PDF（最多 100 页）、CSV、Excel — [Wix Help: Setting Up Menus](https://support.wix.com/en/article/wix-restaurants-setting-up-wix-restaurants-menus-new)；[Wix App Market](https://www.wix.com/app-market/web-solution/wix-restaurants-menus-new)
- Wix 有 Menus API，菜单按 section（Appetizers/Mains…）组织，item 带标签和价格变体 — [Wix Menus API](https://dev.wix.com/docs/api-reference/business-solutions/restaurants/menus/menus/introduction)
- Squarespace 的 Menu block 用于展示餐厅菜单，官方把它定位为 PDF 菜单的替代（对 SEO 更友好）— [Squarespace Menu blocks](https://support.squarespace.com/hc/en-us/articles/206544087-Menu-blocks)
- 餐厅建站评测常推荐 WordPress、Squarespace、Wix 和 Owner.com 等，但都没有给出市场份额 — [Tooltester](https://www.tooltester.com/en/blog/best-website-builder-for-restaurants/)；[Owner.com](https://www.owner.com/blog/website-builders-for-restaurants)

### Inferences
- 菜单发现启发式：① 链接文字或 URL 含 menu/menü/speisekarte/karte/carte/menú/carta/menu del giorno 等 → ② 页面内 `.pdf` 链接（常在 wp-content/uploads、static.wixstatic.com、squarespace-cdn.com）→ ③ 大图画廊（图片菜单，需要 OCR/多模态模型）→ ④ iframe/外链到第三方（预订、点餐或 QR 菜单 SaaS）→ ⑤ JSON-LD 的 hasMenu/menu URL。
- 可以用指纹识别建站平台（Wix：static.wixstatic.com、`X-Wix-*` 头；Squarespace：squarespace-cdn；WordPress：/wp-content/；Jimdo：jimdo 资源域），再按平台走专门的解析器，提高菜单召回。
- 预订组件（TheFork、OpenTable、Resy、Zenchef、Formitable）通常只嵌入预订流程，不承载菜单；TheFork 的餐厅页可能带菜单或价格，但属于平台内容，受其条款约束。这一条未查证。

### Gaps
- 没有 BuiltWith/Wappalyzer 按"餐厅"行业、按欧洲国家统计的 CMS 份额；BuiltWith 的行业数据需要付费。
- QR 菜单 SaaS（Mr Yum/me&u、Sunday、Bbot、menu.app、Menutiger 等）在欧洲的份额、页面结构、ToS 本次都没有检索到。有一项需要单独核实：据了解 Mr Yum 已与 me&u 合并，Bbot 已被 DoorDash 收购。

## 3. Instagram / Facebook 作为数据源：官方 API、Meta ToS 与爬取风险

### Takeaway
官方 Instagram Graph API 的 Business Discovery 可以用"自己已授权的 IG 专业账号"查询**其他公开的 Business/Creator 账号**，拿到 username、name、biography、website、followers_count、media_count 等。前提是必须知道对方的 handle；公开接口不返回联系按钮里的电话/邮箱，个人账号和年龄限制账号也查不到。Meta 的 Automated Data Collection Terms 规定，未经书面许可禁止自动采集。美国 Meta v. Bright Data 案（2024-01）认定"登出状态下抓取公开数据"不违反 Meta ToS，但这一判例不适用于欧洲的 GDPR 分析。

### Cited Findings
- Business Discovery 可取得不由你管理的公开 Business/Creator 账号的元数据和媒体数据；年龄限制的专业账号不返回数据；对返回的 IG Media 直接 GET 会因权限不足失败 — [Meta Business Discovery 文档](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-facebook-login/business-discovery/)
- 调用方式：`GET /{ig-user-id}?fields=business_discovery.username({target}){id,username,name,biography,website,followers_count,media_count}`，website 与 biography 可取 — [jstolpe 示例代码](https://justinstolpe.com/blog_code/instagram_graph_api/business_discovery.php)；[Medium 教程](https://medium.com/@ritikkhndelwal/get-other-instagram-users-data-using-the-python-and-instagram-graph-api-business-discovery-807ba4a9ad91)（二手来源；Meta 官方页面本次没有明确列出 website 字段）
- Business Discovery 适用 Platform Rate Limiting，不适用 BUC 限速 — [Tagembed 汇总](https://tagembed.com/blog/instagram-api/)（二手）
- Meta Automated Data Collection Terms：未事先取得 Meta 书面许可，不得进行自动化数据采集；接受这份条款本身不等于获得许可；采集到的数据只能用于搜索引擎结果或 URL 预览，除非另有书面许可 — [Meta Automated Data Collection Terms](https://www.facebook.com/legal/automated_data_collection_terms)
- Meta v. Bright Data（N.D. Cal.，2024-01，Edward Chen 法官）：Meta 条款"不适用于、也不禁止"Bright Data 在登出状态下抓取公开数据；ToS 中永久禁止抓取的"存续条款"不可执行 — [Courthouse News](https://www.courthousenews.com/federal-judge-rules-against-meta-in-data-scraping-case/)；[Quinn Emanuel 客户通讯](https://www.quinnemanuel.com/the-firm/news-events/client-alert-meta-v-bright-data-significant-decision-for-web-scraping-industry/)；[Zyte](https://www.zyte.com/blog/california-court-meta-ruling/)
- Meta 公开说明其反爬措施（限速、检测、诉讼）— [About Meta: How We Combat Scraping](https://about.fb.com/news/2021/04/how-we-combat-scraping/)

### Inferences
- 实操推荐路径：官网 sameAs / 页脚链接 → 拿到 IG/FB handle（官网来源，合规性最好）；没有官网时再用搜索 API 查 `site:instagram.com "{餐厅名}" {城市}`（见第 4 节）；拿到 handle 后，用自己 IG 专业账号的 Business Discovery 读 bio 和 website，用来交叉验证城市、名称是否匹配。IG 联系按钮里的电话/邮箱不在官方 API 中，只能人工查看。
- 在欧洲，抓取 IG/FB 公开资料还要叠加 GDPR（资料常含个人姓名、个人手机号），法国 CNIL、意大利 Garante 等对"公开数据再利用做营销"有执法先例（本次没有检索具体案例）。低量人工查看加 API 核验的风险远低于批量爬取。
- 美国判例只说明合同（ToS）层面的风险，不能消除欧洲的数据保护风险；已登录状态下爬取仍违反 ToS。

### Gaps
- Facebook Page 公开字段（电话、邮箱、网站）的官方获取途径（"Page Public Metadata Access"功能需通过 App Review）在 2026 年的状态本次没有查证。
- Business Discovery 的具体配额数字（每小时调用数）没有拿到官方原文。
- Meta v. Bright Data 之后的上诉情况或欧洲同类判例没有检索。

## 4. 用搜索引擎 API 补缺失的官网 / 社交账号：2026 年状态、价格与 ToS

### Takeaway
2026 年官方搜索 API 基本退场：Bing Search API 已于 2025-08-11 全部下线；Google Custom Search JSON API 不再接受新客户，老客户也只能用到 2027-01-01。现在可行的选择是 Brave Search API（自建索引，$5/1000，每月送 $5 额度，但存储结果需要带存储权的套餐）和 Google SERP 抓取商 Serper（约 $0.30–1.00/1000）、SerpApi（$25/月 1,000 次起）。后两者抓取 Google 结果，继承了 Google ToS 风险。

### Cited Findings
- Google Custom Search JSON API 官方页原文："closed to new customers"；现有客户须在 **2027-01-01** 前迁移；定价为每天免费 100 次，之后 $5/1000，每天最多 1 万次；官方推荐 Vertex AI Search（适合搜索最多 50 个域名）或联系 Google 了解"full web search solution" — [Custom Search JSON API Overview](https://developers.google.com/custom-search/v1/overview)
- Bing Search API 全系列（Web/Image/News/Custom Search 等）于 2025-08-11 下线，不再接受新注册；微软建议迁移到 Azure AI Agents 的 "Grounding with Bing Search"。后者只给 LLM 代理提供上下文，不返回原始结构化结果 — [Microsoft Lifecycle 公告](https://learn.microsoft.com/en-us/lifecycle/announcements/bing-search-api-retirement)；[cloro.dev](https://cloro.dev/blog/bing-search-api-key/)
- Brave Search API：Search 套餐 $5/1000 次请求，每月自动送 $5 额度，50 QPS；Answers 套餐 $4/1000 加 token 费；FAQ 写明如果要全部或部分存储 API 结果，必须订阅明确授予存储权的套餐（Enterprise 才包含）— [Brave Search API](https://brave.com/search/api/)
- Brave 用自己的爬虫维护 300 亿+页面的独立索引 — [Brave: best search API 2026](https://brave.com/learn/best-search-api-2026/)
- SerpApi：Free 250 次/月；Starter $25/月 1,000 次；Developer $75/月 5,000 次；Production $150/月 15,000 次；Production 及以上含 "U.S. Legal Shield"（抓取和解析搜索引擎数据的法律风险保障，最高 $2M）— [SerpApi Pricing](https://serpapi.com/pricing)
- Serper：新账号免费 2,500 次；$50 买 50,000 credits（$1.00/1000），500k 为 $0.75，2.5M 为 $0.50，12.5M 为 $0.30；credits 有效期 6 个月；每页超过 10 条结果按 2 credits 计 — [Serper 官网](https://serper.dev/)（免费额度）；[coldiq Serper Pricing](https://coldiq.com/blog/serper-pricing)（二手，官网本次没有显示价格表）

### Inferences
- 规模估算：5,000 家餐厅，每家 2–3 次查询（官网 / IG / FB）≈ 10k–15k 次。Serper 约 $10–15；Brave 约 $50–75，减去每月 $5 赠额；SerpApi 需要 Production $150/月。都便宜，选择取决于条款和结果质量。
- 条款取舍：Brave 是自有索引、官方授权，但标准套餐不含"存储结果"的权利。实践中可以只把搜索结果当"指针"，从中解析出目标 URL 后，存自己访问官网或 IG 核验得到的数据；这与 Google Places 的做法类似，属灰度，建议法务确认。Serper/SerpApi 抓的是 Google，Google 条款禁止自动查询，法律风险落在服务商身上，但商业依赖风险仍在（Google 可能随时加强反爬）。
- 查询模板：`"{name}" {city} instagram`、`site:instagram.com "{name}" {city}`、`"{name}" {city} speisekarte|carte|menú filetype:pdf`。

### Gaps
- Brave 各档"带存储权"套餐的具体价格没有公开。
- DuckDuckGo、Mojeek、Exa、Tavily 等其他来源本次没有比较。

## 5. WhatsApp：如何判断号码是否开通 WhatsApp、各国普及率

### Takeaway
官方 WhatsApp Cloud API **已经没有可靠的"号码是否注册 WhatsApp"查询**：旧 On-Premises API 的 contacts 端点改为无论号码是否注册都返回 valid 和 wa_id，On-Premises API 本身也已弃用。市面上的 "number checker" 都依赖非官方 WhatsApp Web 协议，违反 WhatsApp 条款，还有封号风险。实操上可以把官网 `wa.me/…` 或 `api.whatsapp.com/send?phone=…` 链接当成"餐厅主动公开的 WhatsApp"信号；没有这类链接时，默认手机号可能在 WhatsApp 上，但未验证。欧洲 WhatsApp 普及率很高（荷兰、西班牙、意大利、德国在即时通讯用户中都超过 90%）。

### Cited Findings
- 对 contacts 请求的响应"将不再提供准确的状态信息"，无论号码是否关联 WhatsApp，都返回 valid 和 WhatsApp ID — [Meta WhatsApp Business-scoped user IDs 文档](https://developers.facebook.com/documentation/business-messaging/whatsapp/business-scoped-user-ids/)（搜索摘要表述，本次没有逐字核对页面）；On-Premises API 已标注 deprecated — [Postman: WhatsApp On-Premises API (deprecated)](https://www.postman.com/meta/whatsapp-business-platform/collection/vdi189b/whatsapp-on-premises-api-deprecated)
- WhatsApp 正在推出用户名和 business-scoped user ID（BSUID），企业可能拿到的是 BSUID 而不是电话号码 — [CM.com 博客](https://www.cm.com/blog/whatsapp-usernames-for-business-what-you-need-to-know/)
- 第三方的 `/check-exists` 等接口来自非官方网关（如 WAHA、Whapi）— [WAHA contacts controller](https://huggingface.co/spaces/NitinBot002/waha/blob/main/src/api/contacts.controller.ts)；[Whapi dev.to](https://dev.to/whapicloud/source-code-of-the-whatsapp-number-checker-script-2ch1)
- 2025 年 Q1：德国 16–74 岁人群中 83% 使用即时通讯服务（WhatsApp/Signal/Telegram 等），欧盟平均 82% — [Destatis](https://www.destatis.de/Europa/EN/Topic/Science-technology-digital-society/Digital_communication.html)
- 各国 WhatsApp 在即时通讯用户中的渗透率：荷兰 98%、意大利 97.0%、德国 95.5%、西班牙 92.2%（另一口径为 95%）、丹麦 94% — [LINK Mobility](https://www.linkmobility.com/blog/whatsapp-use-in-europe-and-adoption-across-countries)（二手汇总；两处西班牙数字口径不同，存在矛盾）

### Inferences
- 触达设计：WhatsApp 首触达必须由人工在 WhatsApp Business App 中发起，或通过 Cloud API 使用已审批的模板（营销类模板按条计费，且收件人须事先 opt-in）。向从未 opt-in 的餐厅批量发营销模板违反 WhatsApp Business 政策（据已知政策，本次没有抓取原文）。所以 WhatsApp 更适合作为"官网公开了 wa.me 链接"的餐厅的人工渠道。
- 判断号码类型：用 libphonenumber 区分移动与固定号码（如 DE 015x/016x/017x、ES 6xx/7xx、IT 3xx、FR 06/07、NL 06）。固话基本不可能是 WhatsApp，除非餐厅用 WhatsApp Business 注册了座机，这种情况下官网通常会给 wa.me 链接。
- 南欧（ES/IT/PT）餐厅在官网和 IG 放 WhatsApp 预订按钮的情况看起来更常见，但这是经验判断，没有统计来源。

### Gaps
- 没有找到"欧洲各国餐厅在官网公开 WhatsApp 的比例"统计。
- Meta 官方关于 contacts 端点下线时间的原文，本次只拿到了摘要。

## 6. 外卖平台菜单（Deliveroo / Uber Eats / Just Eat Takeaway / Lieferando / Glovo / Wolt）：API 与 ToS

### Takeaway
所有主流外卖平台的菜单 API 都是**"商户或集成商向平台写入菜单"**的方向，只对签约伙伴开放（邀请制，或需要 NDA 和 API 许可协议），没有面向第三方读取公开菜单的 API 或联盟计划。平台条款禁止复制和再利用内容。Apify 等平台上有大量爬虫，但属于违约风险。外卖平台只适合作为"有无外卖/是否在某平台"的信号和人工参考，不适合批量抓菜单。

### Cited Findings
- Deliveroo 开发者条款：API 访问是"临时的、邀请制的"；注册用户才能访问沙盒和部分文档；未经明示许可，不得复制、转载、下载或公开提供其材料；须对其保密信息保密 — [Deliveroo Developers Terms](https://developers.deliveroo.com/terms)
- Deliveroo 的 Menu API 用于 Partner Platform 集成商发布和维护餐厅菜单（价格、库存、过敏原）— [api-evangelist/deliveroo](https://github.com/api-evangelist/deliveroo)（二手概述）
- Uber Eats Marketplace API 面向经批准的餐厅和零售伙伴（主要是 POS 集成），访问需要 Uber 书面批准，须签 NDA 和 API 许可协议并联系伙伴经理；Menu API 用于读取和写入自家门店菜单 — [Uber Eats Marketplace API](https://developer.uber.com/docs/eats/introduction)；[Vorp Labs](https://vorplabs.com/agent-tools/uber-eats-cli)（二手）
- Apify 上有第三方 "Deliveroo Scraper"（菜单和价格）等商品，说明技术上可行，但非官方 — [Apify Deliveroo Scraper](https://apify.com/lentic_clockss/deliveroo-scraper)

### Inferences
- 外卖平台菜单是"外卖菜单"，价格常高于堂食，菜品也可能是删减版。对菜单设计和印刷来说，它能说明菜系、价位和菜品数量，但不能替代实体菜单。
- 建议只记录餐厅在哪些平台有店（通过搜索 API 的 URL 判断，例如 deliveroo.co.uk/menu/…、lieferando.de/speisekarte/…），不抓内容。

### Gaps
- Just Eat Takeaway / Lieferando、Glovo、Wolt 的开发者条款和消费者 ToS 中关于抓取的具体条款，本次没有逐一查证。
- 各平台是否有联盟（affiliate）计划，以及联盟是否包含菜单数据：没有找到任何来源，推测都不提供。

## 7. 爬取实务：robots.txt、限速、JS 渲染、反爬、成功率

### Takeaway
对小型餐厅官网（每站抓 3–8 页）来说，技术难度主要在 JS 渲染（Wix 等）和 PDF/图片菜单解析，反爬不是主要问题。没有找到"餐厅官网抓取成功率"的公开统计，应在试点中实测。

### Cited Findings
- Brave Search API 50 QPS、Serper 每页超过 10 条结果计 2 credits 等搜索侧限速和计费见第 4 节 — [Brave Search API](https://brave.com/search/api/)；[coldiq](https://coldiq.com/blog/serper-pricing)
- Meta 对爬虫做了检测、限速和诉讼等反制 — [About Meta](https://about.fb.com/news/2021/04/how-we-combat-scraping/)

### Inferences
- 推荐管线：httpx 静态抓取 → 检测到 Wix/Squarespace 或空壳 SPA（正文文本 < N 字、含 `__NEXT_DATA__`、有 wix-thunderbolt 等标记）时，才回落到 Playwright 渲染。PDF 用 pdfplumber 或 PyMuPDF 提取文字，扫描件和图片走 OCR 或多模态 LLM。
- 礼貌抓取：遵守 robots.txt；同一域名 ≤1 req/s、并发 1；UA 写明联系方式；全量抓取周期按 90 天刷新。欧盟 DSM 指令第 4 条的 TDM 例外允许权利人用机器可读方式保留权利（本次未取得原文），可以把 robots.txt 或 TDM 保留声明视为选择退出的信号。
- 预期成功率（经验估计，无来源）：有官网的餐厅中，电话几乎 100% 可得；邮箱在 DE/AT 高（Impressum 强制），FR/ES/IT 中等；IG 链接较高；菜单能找到的可能占 60–80%，其中相当比例是 PDF 或图片。以上都需要试点抽样验证。

### Gaps
- 没有找到餐厅或中小企业官网的抓取成功率、Cloudflare 拦截率、JS 渲染占比等公开实测数据。
- 没有找到欧洲餐厅菜单格式分布（HTML/PDF/图片/第三方）的公开统计；前一份笔记同样缺失。
