## v0.3 新增决策（2026-09-30）

- D13：T0/T1 技术条件与 B 触达条件分离；毛利、销售账号和客户回复不阻断内部研究及最小工具。
- D14：T0 → T1 → D → V；B 可在 T1 后并行，M 才按商业证据决定扩大投入。
- D15：开发按 development.md 的 D1～D10 验收；先单家闭环后批量续跑，每项有输入、输出和失败路径。
- D16：当前仅测人工任务与审批/抑制；未来自动发送才增加 webhook、对账及停发竞态测试。
- D17：setup、processing、outreach 成本分列；保留总投入，比较同等质量的人工与工具处理时间。

以上方向经本轮用户确认；城市及经营数值仍未代为确定。

## Monorepo 约定（2026-09-30）

D18：采用同仓库的 `apps/web` 与 `apps/api`，前后端独立构建与部署；后端按业务模块组织，暂不拆微服务。共享 API 客户端按需生成；pnpm 与 uv 分别管理依赖，不强制引入 Turborepo。

## T1 后决策（2026-09-30）

- D19：研究区域 Islington，目标类型为 FSA 类型 1 中的独立或小型集团堂食餐厅；抽样按 FHRSID 排序后固定种子随机抽取，排除 AwaitingInspection。用户尚未确认试点城市，此为技术探索选择。
- D20：首版支持格式为文本型 PDF（含坐标分栏）与 HTML 文本；图片与扫描件进入人工/视觉队列；抓取被拒站点转人工下载。依据：5 份菜单中 PDF 3、HTML 1、图片 1，且无模型密钥。
- D21：样稿渲染先用本机 Chrome 无头模式（零依赖）；部署环境改用 Playwright Chromium，模板不变。
- D22：D1～D10 时间盒 11 人日（exploration.md 五）；超出先缩范围。
- D23：抓取脚本统一用 `uv run --python 3.12`，系统 Python 3.9 存在 TLS 握手失败。
- D24：后端不引入 Celery/Redis；批量处理为同步逐 job 执行并持久化状态（≤100 家），更大批次再评估队列。
- D25：数据库驱动用 psycopg 3（LGPL-3.0，作为未修改的库使用）；其余核心依赖为 MIT/BSD/Apache（fastapi、sqlalchemy、alembic、pydantic、pdfplumber、httpx）。LGPL 未列入项目排除清单，正式上线前由负责人确认。
- D26：真实模型 provider 暂未接入（无密钥）；`engine=provider` 仅 FakeProvider，结果一律 needs_review，不作为验证依据。
- D27（V 后）：HTML 菜单提取采用 DOM 关联（价格节点→同卡片内标题/加粗文本），并输出 PDF/图片候选；按行匹配仅作兜底。
- D28（V 后）：`BEACON_FETCH_IP_CHECK` 默认开启；仅在解析器把域名映射到代理地址的环境关闭，关闭后字面量内网地址仍阻断。
- D29（V 后）：人工可在分析上新增问题与菜品（`issues[new]`/`items[new]`），必须带证据位置，并记为人工确认；用于图片菜单转录。
- D30（V 后）：下一批 50 家由真人执行并计时以取得人工基线；视觉路径评测优先于 Squarespace 渲染。
- D31：真实 provider 选 Anthropic（`anthropic` SDK 1.9.0，MIT），默认模型 `claude-opus-5-5`、effort medium，结构化输出（`messages.parse`）；系统提示禁止推断过敏原/成分/利润，观察必须带位置。未经真实密钥验证前，D26 的“不作为验证依据”仍然成立。
- D33：取消“纯人工 vs 工具”对照作为第二批主设计（用户 2026-09-30 确认：系统是客户员工使用的工具，与纯人工比较意义有限）。第二批改为真人用工具处理全部 50 家并六步计时，产出每家处理成本与可用性问题清单；纯人工对照降为可选，仅在需要对外“节省工时”数字时抽约 10 家做。`scripts/assign_arms.py` 保留分组能力供可选对照使用。
- D34（2026-10-01）：接入 Companies House 名称检索作为主体核对的辅助（`GET /api/leads/{id}/entity-candidates`）。只返回候选与登记事实（编号、状态、类型、注册地址、SIC），不自动写主体状态；人工采用并保存后才记为 company，证据文本含公司编号、检索词与日期。未查到不推断为个体经营；注册邮编不一致不作排除依据。检索结果不入库。“暂缓 Companies House 主体自动判断”不变。测试用模拟响应；真实调用已在 api 容器内验证（3 家线索，需 live 应用下的 REST key，Test 应用的 key 调正式接口返回 401）。
- D35（2026-10-01）：主体候选改为三路合并，因为单靠店名检索噪音太大（20 家里 18 家填满 10 条，多数与门店无关）。可靠性从高到低：官网披露的公司编号/公司名（规则提取后按编号精确查）、注册邮编与门店一致的餐饮类在营公司（门牌号一致再加权）、店名检索。默认只展示依据较强的候选，其余折叠；仍只给候选，人工采用并保存才生效。无官网的门店靠注册邮编一路，另在操作手册写入“场所许可登记”人工步骤，不做自动化。实测 40 家（有官网、无官网各 20）：官网找到公司编号 2/20；注册地址门牌一致 18/40，其中唯一一家 12/40；默认展示 0 个 8 家、1 个 9 家、2～3 个 11 家、4 个以上 12 家。候选是否为真实经营主体未经人工核对，以上只是检索覆盖情况，不是准确率。相似度门槛 0.5 与“同邮编不超过 3 家全部展示”为经验值。
- D36（2026-10-01）：新增联系方式查找（用户要求：销售触达需要各种联系方式与社媒账号）。来源为官网页面（规则提取邮箱、电话、WhatsApp 链接、社媒账号、联系表单）与已存的 Overture 电话/社媒；只给候选，人工勾选后记为渠道准入行，可用性与准入都是 unknown，已有行不覆盖。渠道枚举增加 `facebook`、`tiktok`、`other_social`（X、LinkedIn、YouTube），与 Instagram 一样只记录、暂缓触达。“找到联系方式”与“允许使用”仍分开：unknown 不放行，各渠道规则不变。个体经营者的联系方式属于个人数据；可能指向个人的邮箱在候选里标出，保留期与抑制规则沿用现有约定。实测 40 家（只读，未写库）：有官网的 20 家全部找到至少一种（电话 19、Facebook 17、邮箱 9、Instagram 9、TikTok 3、联系表单 3），其中 5 家含可能指向个人的邮箱；无官网的 20 家只有 2 家有（来自 Overture）。候选是否属于门店未经人工核对。
- D37（2026-10-01，用户确认）：批次可删除，不论是否处理过。只属于该批次的门店及其全部数据与文件一并删除；属于其他批次的门店保留。例外：有拒收/退订抑制记录的门店不删（脱离批次保留），因为删掉后同一门店重新导入会丢失抑制，违反“拒绝/退订进入抑制记录”。删除需输入批次键确认并写审计日志（只记数量）。已发送任务等真实联系记录会随门店删除，界面在删除前提示。新建批次的地区改为下拉，选项取 FSA 英国地方当局名录，国家固定 GB。新建后默认自动建名单（FSA 抽样 50 家、Overture 补全、规则预筛），可关闭；抽样数与种子在新建时填写并随批次记录。
- D38（2026-10-01，用户要求有官网就自动取联系方式）：联系方式改为可批量自动记录，作为批次运行的 `contacts` 步骤并接入新建批次的自动流程。自动记录的仍是 unknown/unknown 行，不放行、不覆盖已有审核结果、不记抑制名单里的；这把 D36 的“人工勾选后记录”放宽为“自动记录、使用前人工核对准入”。为控制噪音：筛选排除的门店不查；官网上同一类型超过 5 个时只记 Overture 也有的。长任务分块执行（每次 20 家），避免单个请求超时；块内用线程池并行读官网（最多 8 个站点，同一主机串行），数据库写入仍在主线程逐家进行。实测 26 个站点并行 28.7 秒，逐个访问的耗时合计 188.5 秒；下限是最慢的那个站点（23.7 秒）。自动记录的联系方式可能含第三方或相邻门店的信息，未经人工核对。
- D32：PDF 规则支持一行多价拆分（" / "、" | "、" • " 分隔且每段以价格结尾）；规则版本 0.5，批次规划按版本重跑。

- D39（2026-10-03，审查修复）：联系方式抓取只要有页面失败，job 标为 failed，但提交并保留成功页面已记录的联系方式；支持原运行 resume 或新建运行重试，完整成功后跳过。重试仍扫描当前官网的相关页面，通过现有记录去重，不在前端自动循环重试失败任务。YouTube 账号路径保留大小写，不修改历史已存联系值。

## 保留原则

- 固定、可审计工作流；模糊判断交模型，结果需证据与审核。
- 如需队列采用 Celery，不同时建设 n8n 核心流程。
- 模板生成局部改版，不直接生成含菜名价格的整张 AI 图片。
- 不引入项目政策排除的 AGPL/GPL 或限制当前用途的依赖；核对确切版本。
- 不使用非官方 WhatsApp 群发库或 Google Maps 抓取数据。
