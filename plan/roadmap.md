# Beacon 路线图（Roadmap）

版本：v0.3，2026-09-30。已确认先整理验证流程，后确认英国试点且没有现成名单；尚未抽样。当前无应用代码、构建系统或自动化测试。本次不采集名单、不触达。

依据：[产品方案](../欧洲餐厅菜单设计与印刷获客系统方案.md)、[决策记录](decisions.md)。进度见 [tasks.md](tasks.md)，操作细则见 [validation.md](validation.md)，开发交付合同见 [development.md](development.md)。旧版保留在 [历史快照](archive/2026-09-30-v0.1/README.md)。

## 一 目标与边界

先验证能否用合理人工成本，找到有真实菜单问题、允许联系且有购买兴趣的餐厅。先约 10 家技术探索，再约 50 家扩大验证；样本用于发现流程瓶颈，不用于证明成交率或全年回报。

验证版保留：名单导入、菜单分析及证据、人工审核、一个局部改版模板、联系任务与结果记录。暂缓：多源自动同步、复杂评分、自动跟进、完整 CRM、生产印刷文件、多国和多租户。

## 二 阶段、依赖与两类门槛

| 阶段 | 进入条件 | 交付与退出条件 |
|---|---|---|
| T0 技术准备 | 英国试点方向已确认 | 落实研究地区、来源/许可、执行人、受控存储与研究工时/费用上限；不要求毛利、销售账号或联系授权 |
| T1 技术探索 | T0 技术条件齐备 | 约 10 家真实候选的获取/解析路径、失败记录、人工耗时；至少一份真实菜单跑通提取→证据→人工确认→局部样稿；据此确定首版支持格式 |
| D 最小工具 | T1 有可复现路径，首版范围及开发时间盒确定 | 按 development.md 的 D1～D10 实现导入到结果记录；先一家跑通再批量；不等待客户回复或成交 |
| V 扩大桌面验证 | D 的单家流程可用；批处理评测前 D10 完成 | 约 50 家新候选，冻结样本/版本，对照人工与工具耗时；报告质量和单位持续成本 |
| B 人工商业验证 | 有已审核素材，经营预算、身份、销售负责人和逐条准入齐备 | 人工联系并完成观测，给出意向、成本和继续投入结论；可使用表格先行，不依赖 D/V 完成 |
| M 后续投入决策 | 技术和商业证据可用；缺少一类时明确限制 | 决定是否扩大自动同步、自动跟进、评分等投入，重新估时和报价 |

依赖主线为 T0 → T1 → D → V。B 可在 T1 后与 D/V 并行，销售准备不阻断技术研究，商业观测窗口不阻断最小工具交付。M 的规模化投入需要相应商业证据；没有实际触达时不声称获客有效。

T1 的失败也是交付：若没有真实菜单跑通，先修正数据/解析路径，不盲目搭工作台；单一格式跑通可限定首版仅支持该格式，其他格式进入人工处理。

研究和开发均有预算边界：T0 冻结研究上限，T1 报告后按 D1～D10 分别估算并给出开发时间盒；超出上限先缩范围并记录，不无限扩展。旧版 41 人日、34～50 人日和 5.8 万元均为历史范围估计，不作为新版承诺。

## 三 验证版架构

- 桌面阶段：CSV/本地脚本和受控证据目录；成熟的复现脚本放 `scripts/`。真实联系人、菜单和凭证不提交 Git。
- 开发阶段：FastAPI + PostgreSQL；有后台任务需求时使用 Celery + Redis；需要工作台时采用 Next.js + Ant Design，不在验证前一次搭齐。
- 模型：一个实际 provider + `FakeProvider`，保留可替换接口；先评测再增加厂商。
- 菜单：HTML/文本 PDF 优先确定性提取，扫描件和图片按样本选处理方案；保留文本和版面证据。一个 HTML 模板生成审核用 PNG/PDF，不承诺印刷生产规格。
- 发送：验证期人工执行和回填；后续接入一种符合业务条件的服务，避免两套节奏引擎。
- 依赖：引入前核对用途、确切版本许可证及数据处理安排；继续遵守项目排除 AGPL/GPL 等依赖的政策。

采用 Monorepo：`apps/api/`、`apps/web/`、按需创建的 `packages/api-client/`，以及根目录 `templates/`、`scripts/`、`infra/`；后端夹具放在 `apps/api/tests/fixtures/`。模块边界见 [开发说明](development.md)。尚无运行命令；首次实现时更新 `AGENTS.md` 和 `CLAUDE.md`。

## 四 数据与审核约束

| 对象 | 最小要求 |
|---|---|
| 餐厅与主体 | 门店和法律主体分开；记录匹配证据、置信度、审核人；未知不推断为公司 |
| 联系方式 | 渠道、规范化值、来源和时间；可用性与准入独立记录 |
| 渠道准入 | `unknown/allowed/blocked`、规则版本、证据、审核人、复核时间；授权另记范围、取得时间与撤回 |
| 菜单与问题 | 来源、采集时间、文件 hash、页码/位置/截图、事实描述、人工确认 |
| 内容与审批 | 菜名/价格来源、内容 hash、模板及模型版本、审批人；修改后重新审批 |
| 任务与事件 | 计划渠道、实际发送时间、回填时间、销售、结果；打开链接不计发送 |
| 回复与抑制 | 对方回复时间、系统收到/录入时间、拒收范围、动作、事件幂等键 |

采集数据和派生数据分别记录来源；内部状态无需伪造外部来源。原始 JSON、日志、缓存、文件和备份同样纳入存储政策，不能只检查主表字段名。

按数据类别确定保留期、删除/匿名化规则与执行记录；拒收匹配仅保留必要信息，审计不是无限期保存原文的理由。

## 五 渠道与停发边界

以 [验证细则](validation.md) 为当前准入基线。未确认渠道默认 `unknown`，不能创建可执行发送任务。每日限额和人工点击均不能替代许可。

验证期销售每次联系前检查最新抑制记录；看到人工回复即暂停并回填，未核对回复时不继续该线索。

未来自动发送必须满足：

1. 发送入口再次检查准入、审批和抑制状态；排入队列不等于获得永久许可。
2. 系统收到或录入停发事件后立即提交抑制状态，60 秒内取消系统内未执行任务，并记录延迟。
3. 已交外部服务的请求记录取消结果，不承诺撤回；外部提交与停发并发时保留审计。
4. 超时结果未知先对账，不盲目重发；重复 webhook、重试和录入不得重复执行动作。
5. 人工平台消息依赖销售回填，不承诺对方回复后 60 秒内自动获知。

## 六 排序与菜单分析

取消六维总分和 70 分门槛。先以“目标类型符合 + 有人工确认问题 + 至少一个允许渠道”建立可联系集合，按问题影响、证据完整性、人工工作量排序。缺失记未知，保留理由。

首期检查低清、移动阅读困难、文字溢出、价格/货币格式不一致；原始测量仍须人工解释和确认。不判断高利润菜品、不比较未取得的外卖菜单、不将缺双语等同缺陷、不推断或补写过敏原及素食成分。主观设计意见标为建议。

## 七 测试与验收

文档期核对链接、计数、状态和约束一致性。T1 的约 10 家全部可用于探索，不宣称独立验收。V 使用新批次，保留输入、版本、输出及修正；至少留 20% 作为冻结验收集，按实际菜单格式报告数量，不为凑格式比例替换候选。

代码出现后采用 pytest；有前端时用 Vitest/Testing Library，关键审核流程用 Playwright。外部接口默认模拟，模型用 `FakeProvider`，真实模型评测单独记录成本。

当前 D 阶段覆盖：未知准入阻断执行任务、拒收阻断、审批后修改失效、主体错配、缺失证据、导入及分析重试、重复手工事件和权限检查。无需实现外部发送器、webhook、送达追踪或其测试。未来接入自动发送时才加入发送超时、对账、重复 webhook 和停发竞态测试；第五节的自动发送要求属于后续阶段。核心规则逐项覆盖，全局覆盖率不作为开工条件。

对外菜名和价格逐项核对；失败进入人工处理。报告写实际分子/分母，不把样本零错误外推为线上保证。性能先记录实际耗时、文件大小和成本，再确定服务目标。

## 八 协作与完成定义

功能分支按 `feat/<阶段>-<主题>`；按可独立审核的改动拆 PR，不强制一个阶段一个大 PR。分支保护和 CI 实际配置后才声称生效。

任务完成需有交付物、复核结果和文档状态；代码任务另需相关测试通过。没有实施的能力、没有运行的验证均不标完成。实现时维护 Ruff、mypy 和可执行 CI，不提前编造命令。
