# Beacon 最小工具开发交付说明

版本：v0.3，2026-09-30。本文是计划，尚无实现。依赖与进度以 [路线图](roadmap.md)、[任务清单](tasks.md) 为准。

## 一 开工与交付边界

T1 先用约 10 家真实候选验证获取和解析路径，至少一份菜单走完证据、人工确认和样稿。开发不等待 B 的销售结果。T1 结束后确定支持格式、每项估时和总时间盒，再执行 D1～D10。

首版为一个内部工作台，FastAPI + PostgreSQL，简单 Next.js 页面；无邮件发送和自动联系能力。Celery/Redis 仅在任务执行确有需要时引入，不能先成为骨架前置条件。先一家端到端可用，再做批次处理。

## Monorepo 目录与模块边界

前后端同仓库、独立应用；后端按业务模块组织，不拆微服务。目录按任务创建，不预建空包。

```text
apps/
  web/                       # Next.js 工作台，独立测试与构建
  api/
    pyproject.toml           # Python 依赖与工具配置
    app/
      modules/
        leads/               # 门店、批次、导入
        menus/               # 菜单、解析、问题证据及修正
        content/             # 样稿、文案、版本审批
        sales/               # 准入、人工任务、回复、抑制及成本
      core/                  # 配置、认证、数据库连接
      integrations/          # 模型、网页获取、文件存储适配
    migrations/
    tests/fixtures/          # 脱敏夹具
packages/
  api-client/                # 需要时从 OpenAPI 生成的前端客户端
scripts/                     # 研究、导入、评测命令入口
templates/                  # 菜单样稿模板
infra/                       # 本地运行与部署配置
```

Python 依赖由 uv 管理，前端及 TypeScript 包由 pnpm workspace 管理；不强制引入 Turborepo。模型适配器不得自行修改审批或销售状态；业务模块通过明确服务接口协作，避免跨模块直接修改内部状态。

研究脚本先验证路径；成熟处理逻辑迁入 `apps/api/app/`，脚本与 API 共用，避免维护两套解析实现。共享包只在存在真实调用方时创建；前端 API 类型以服务端 OpenAPI 为源，不手工维护第二套契约。需要 worker 时复用后端业务逻辑，不提前拆成微服务。

## 二 开发任务合同

以下为拟定交付接口与行为，D1 固化 schema 时可调整命名，但不得丢失验收行为。接口统一在 `/api` 下。

| ID / 依赖 | 输入 | 输出与建议接口 | 验收及失败路径 |
|---|---|---|---|
| D1 / T1 | 探索记录、最小字段表 | 固定支持格式与大小上限、实体/状态 schema、依赖版本、逐项估时；本地 API/数据库、迁移、测试命令 | 空库可初始化；必要配置缺失时明确报错；命令实测后入指南；不要求先搭队列 |
| D2 / D1 | 单操作者试点身份、存储路径 | 访问保护、会话、统一当前操作者、受控文件访问；`.env.example` 和 Git 忽略规则 | 未认证不可读取/修改记录或直接下载文件；权限以服务端为准；开发阶段可仅本机访问，网络部署前复核访问控制 |
| D3 / D2 | 批次元数据、FSA 标识/来源键、CSV | `POST /imports`、`GET /leads`；逐行结果与错误明细，稳定 lead_id | 同批次同来源键重导不新增门店；同一门店跨批次关联；坏行明确拒收；不按店名自动合并不同地址 |
| D4 / D3 | 人工核对的菜单 URL 或本地文件 | `POST /leads/{id}/assets`、来源/时间/hash、受控文件引用、处理状态 | 文件超限、格式不支持、404、超时有原因；失败可重试；URL 抓取阻断本机/内网及重定向绕过；外部抓取有时限 |
| D5 / D4 | T1 支持的菜单格式、一个 provider 或 FakeProvider | `POST /assets/{id}/analyses`；菜品/价格、问题候选、原文/位置证据和版本 | 至少一份真实格式跑通；schema 错误或无证据进入人工处理，不能伪装成功；重试保留关联与版本，不重复创建相同有效结果 |
| D6 / D5 | 分析结果、原始证据、人工修正 | `PATCH /analyses/{id}`；证据与修正同屏，新版本和修改记录 | 原始值不覆盖丢失；价格修改可追溯；无可核对证据的问题不能作为确认事实发布；正常无问题可完成审核 |
| D7 / D6 | 确认数据、一个模板 | `POST /leads/{id}/content`、`POST /content/{id}/approve`；局部样稿、短文案、内容 hash | 菜名价格与确认数据一致，长文本不溢出；审批针对具体版本；内容或源数据修改使依赖审批失效，不新增过敏原等事实 |
| D8 / D7 | 渠道准入/证据、审批版本、拒收状态 | `POST /leads/{id}/tasks`；人工任务及状态，创建前复核准入 | unknown/blocked、证据失效、未审批或已抑制不生成可执行任务；点击只记录打开；记录人工发送需操作者和发生时间，不调用发送 API |
| D9 / D8 | 人工回复、事件键、发生/录入时间、费用/工时 | `POST /leads/{id}/events`、`GET /batches/{id}/summary`；暂停/抑制及汇总导出 | 相同事件重复提交不重复动作；拒收保存即使待办不可执行；回复先暂停；跨渠道按门店去重，零分母写不适用，成本三类分列 |
| D10 / D3～D9 | 单家已打通流程、脱敏夹具、支持格式基线 | 小批次独立任务状态与续跑，核心测试、操作手册、备份恢复演练 | 一条失败不终止整批；重启后能看见失败/未完成并安全续跑；重复导入不重复任务；单家完整流程与主要失败路径通过，恢复后记录/文件关联一致 |

## 三 页面与状态

仅三组页面：线索列表/导入及批次统计；详情中的菜单证据、修正与样稿审批；人工任务/回复回填。保留审核人和执行人记录，首版可同一操作者，不先做复杂 RBAC。

分析状态：`pending → running → succeeded/needs_review/failed`，失败记录原因；重试是有版本的尝试。审批状态：`draft → approved/rejected`，修改后回到 `draft`。人工任务：`pending → opened → sent_manual`，也可到 `paused/cancelled`；`opened` 仍须通过最新准入/审批/抑制检查才能继续。

菜单版本、分析版本、内容版本及任务相互关联。源数据更正后，取消或暂停引用旧内容的未完成任务；历史已发送记录保留原版本。准入状态必须由审核证据支持，模型不能自行把 unknown 改成 allowed。

## 四 验证与范围控制

每个任务在 PR 中写实际输入样例、输出、成功/失败验证和依赖。先完成 D3～D9 的单条流程，再交付 D10 的批量续跑；D 阶段不以销售意向或成交率验收。

pytest 覆盖 API 和规则；前端关键修改/审批状态用 Vitest/Testing Library，完整人工操作流程用 Playwright。真实模型评测单列，普通测试使用 FakeProvider。不为将来的自动发送编写空壳服务或无实现测试。

一次性开发时间计入 setup；日常研究与纠错计入 processing；实际销售操作计入 outreach，详见 [验证流程](validation.md)。性能与质量门槛根据 T1 基线冻结，不提前承诺任意菜单全自动成功。

## 首轮交付与审查

Claude 首轮从 T0/T1 开始：落实技术取样和研究边界，交付可复现的约 10 家探索结果、失败原因、支持格式及人工回退。技术条件齐备后按 D1～D10 推进，不一次实现历史全量 MVP，也不等待销售回复。

每批交付说明改动范围、实际运行命令、测试结果、已知限制和未完成项；同步任务状态。真实接口或凭证不可用时说明限制，不能用 FakeProvider 结果冒充真实模型验证。审查优先检查功能偏差、数据版本、审批失效、拒收约束、失败恢复及测试有效性。

## D45：AI 自动补全官网与菜单（施工计划，2026-10-11）

用户已授权准备实施。目标：从逐步人工确认改为单家一键研究，证据明确时自动采用官网、获取菜单并生成待审核分析；冲突或不足时给出具体复核原因。D44 已有发现与抓取能力。单家链路已实现并通过隔离界面验收；多家质量评测及批量入口仍未完成。以下为施工设计，实际首版限制见本节末尾。

### 实施顺序

1. **证据与模型接口**：复用已配置 DeepSeek 的凭证与 HTTPX，新增结构化文本判断接口及 Fake 判断器；与菜单转录接口分离。输入只提供门店基本信息、候选官网页面的有界文本与来源链；Google 价格、照片不送模型。页面内容视为数据，不能执行页面指令。输出候选 ID、官网/分店关系、菜单类别、明确日期或未知、引用证据 ID 与逐条原文，以及 accept/review/reject 与原因。记录模型/提示版本、调用时间和用量；未配置真实模型时提示不可用，Fake 不用于生产自动采用。
2. **官网自动判断**：优先评估已有官网和已关联 Places 的官网候选，读取首页及联系方式/门店页。首版沿用已核对 Google 门店关联；未关联仍可处理现有官网，不自动挑选 Place ID。AI 给出匹配理由，程序检查引用是否来自本次页面、原文是否存在。自动替换需有独立身份锚点（官网完整地址与门店一致，或已知电话一致并有门店地址证据），不能只凭店名、搜索排名或模型自报置信度。集团链接提供运营关联依据，仍需分店身份匹配。地址/邮编/电话冲突、第三方平台、同名分店或证据不足进入复核；任何明确冲突优先于正向判断。
3. **菜单自动判断与处理**：复用 5 页官网发现；优先 PDF、其次图片/HTML。最多评估 6 个文件，沿用抓取大小限制；先在受控暂存区检查内容，确认后再成为正式资产，拒绝及未确认文件不生成成功资产或分析。文本 PDF 用规则提取证据，扫描件用现有视觉模型；AI 判断店名/分店、饮品/食物/套餐/优惠类别。已确认分店官网直接链接的菜单、内容确为菜单且无归属冲突，允许自动导入；相同内容按 hash 去重。日期缺失记未知，不据文件名宣称当前有效；明确过期优惠进入复核。已接受菜单接现有规则/模型分析，分析结果保持 needs_review。
4. **单家工作流与界面**：增加“自动补全官网与菜单”，展示阶段、官网选择依据、各文件处理结果、待复核原因及失败重试入口；人工路径继续可用。官网自动采用注明 AI + 程序校验，保存旧 URL、来源、证据及模型版本，不能伪造人工审核人。更新编辑框并重置联系方式扫描标记；已有联系方式及准入保留。长操作采用可查询的运行记录与后台任务，首版不新增 Celery/Redis；中断标记并可重试，不声称跨重启自动恢复。
5. **验证后开放批量**：先用 College Bar 跑真实模型与官方 PDF 链路，再固定约 10 家名单，包含同名异店、集团官网、多个分店、无菜单、过期优惠、扫描件和失败网站。报告真实自动接受/复核/失败数量、错官网及串店数、耗时、用量/成本，保留验收依据。首版交付不包括批量入口；评测后再确定阈值和批量限额。

### 事务、重试与边界

- 同家并发启动只允许一个活动运行；模型/网络期间不持有数据库行锁。采用前重新检查官网与 Google 关联修订，发生变化则标记冲突，不能覆盖用户编辑。
- 每步记录状态与结果；已获取文件和分析按运行/内容幂等重用，失败重试不重复导入。限制页面数、文件数、模型调用数与请求时间；达到上限保留部分结果和具体失败。
- 模型 JSON 非法、证据引用错误、页面指令干扰、超时、验证码、PDF 无法读取均不能自动通过；保留可解释的人工处理入口。
- 不自动批准菜单价格、设计问题、营销文案或渠道准入，不触达客户。无需 Google 登录；动态官网 Playwright 渲染和 Maps 登录抓取不在本次首版范围。

### 验收用例

| 场景 | 预期 |
|---|---|
| College Bar 新官网地址一致且官方 PDF 归属清楚 | 一键采用、获取、分析，展示依据；价格待审核 |
| 同名异地、集团页未定位分店、地址冲突 | 不自动覆盖官网或导入不确定菜单，说明冲突 |
| 引用不存在、AI 只报高置信度、网页诱导指令 | 校验失败，不自动通过 |
| PDF 为隐私文件/过敏原说明/明确过期优惠 | 排除或复核，不冒充有效菜单 |
| 用户在运行中改官网或 Google 关联 | 采用前冲突检查阻止覆盖 |
| 重复点击、同文件多个 URL、失败后重试 | 单一活动运行，不重复资产或分析 |
| 真模型未配置、超时、输出截断 | 明确失败/待复核，不用 Fake 结果冒充 AI 已确认 |

测试覆盖上述关键失败路径；运行相关 pytest、Ruff/mypy、前端类型/测试/构建，并用隔离库核对界面。真实评测单列，模拟测试通过不等于自动判断质量已验证。

### D45 单家首版实现与实际限制

- 后端 `leads/auto_research.py` 与 `integrations/research_judge.py`；前端 `AutoResearch.tsx`。POST 启动，GET 查询当前运行。状态保存在 `lead.raw`，历史启动/官网采用/菜单导入/完成有审计。同步步骤在 FastAPI BackgroundTasks 中运行；部署须单 API worker，重启或超时后状态查询标为 interrupted，可手动重跑，不自动续跑。
- 最多评估 3 个官网（每个首页加至多 2 个相关页）；可从集团官网发现名称相关的分店外链，排除常见社媒。AI 接受且同页完整街道/门牌与邮编匹配才自动采用；目前没有独立电话替代规则。官网菜单发现仍为最多 5 页，评估前 6 个文件。文件暂存内存，文本 PDF 证据取前 12 页；扫描件用现有视觉接口，结果为转录证据，不伪装原始 OCR 正确率。
- 证据引用必须是原文子串；错误引用允许 1 次 AI 修正，仍错就失败。模型不得把 PDF 表格列拼成“原文”，不得把文件名/链接元数据当正文日期。菜单自动导入还要求实际文件中的菜单引用及至少两处带 £/€/$ 前缀的价格；优惠日期不明留复核。缺日期不宣称当前有效。
- 运行间采用文件 hash 去重；已有资产/分析复用，已人工审核的版本保持原审核。新分析一律 needs_review。官网、身份资料及 Google 关联在写入前复核；不持有网络请求期间的门店行锁。
- 本次不开放批量，不处理 Maps 登录抓取，不改渠道准入，不触达客户。真实模型使用既有 DeepSeek 配置；Fake 不允许生产自动采用。
