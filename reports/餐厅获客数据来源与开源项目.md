# 开放数据打底，官网补全，Google 只做指针

**结论：欧洲餐厅获客名单最合适的底库是免费、允许入库的开放数据，不是 Google Places。** 2026 年 9 月对 Overture Maps Places 的实测显示，伦敦、都柏林、阿姆斯特丹三个城市的餐厅记录中，**电话覆盖 89–93%、官网 80–84%、社媒 80–93%、邮箱 36–53%**，餐厅数量约为 OSM 的 2–3 倍。数据许可为 CDLA/Apache/CC0，可以商用、落库，也没有 ODbL 的共享义务。Google、Foursquare 付费 API、Yelp、HERE、Mapbox 的条款都禁止或严格限制长期存储，只能在线索详情页里实时显示评分和价位。WhatsApp、菜单、负责人姓名这三样，任何 API 都不提供，只能从餐厅官网自己采集。欧洲各国法律要求官网公开联系方式和经营者身份（德奥 Impressum、法国 mentions légales、西班牙 aviso legal），这些页面因此是最稳定的采集入口。"新开业"信号要看政府登记：英国 FSA 食品卫生评级里的 "AwaitingInspection" 记录、Companies House 新成立的 SIC 56101/56102 公司、法国 SIRENE 按门店记录的创建日期，都比任何商业 API 更早、更准，而且免费。综合数据完整度和上一轮已确认的合规边界，**首个试点应放在英国**，数据组合为 FSA、Overture、Companies House 和官网自采，数据成本接近零。开源方面，采集、抽取、菜单解析、样品渲染四层可以直接复用 Apache/MIT 组件（Crawl4AI、extruct、phonenumbers、Docling、Playwright）。线索评分、序列编排、销售工作台没有成熟的开源项目可用，应当自研。原方案技术栈中的 n8n 采用 Sustainable Use License，不应放在交付物的核心位置。

## 方法说明：实测数据与 GitHub 公开 API

本报告综合了五份调研笔记，并沿用上一轮可行性研究中仍然成立的结论（合规分区、Google 定价与 OSM 城市覆盖率）。标注"实测"的数字来自 2026-09-25 的直接查询：Overture 数据用 DuckDB 读取官方 S3 上 `2026-09-23.0` 版本的 Parquet 文件，按城市矩形范围统计 `basic_category='restaurant'`；FSA 数据来自其 API V2；丹麦数据来自 Smiley XML 原始文件；OSM 数据来自 taginfo API；Companies House 数据来自其网页 Advanced Search。矩形范围比行政区略大，所以各城市数字只用来比较数量级。**本次调研没有安装 GitHub 插件。所有开源项目的 stars、许可证（SPDX）、最近推送时间和主要语言，均于 2026-09-25 通过公开的 GitHub REST API（`/repos/{owner}/{repo}` 与 `/search/repositories`）获取。** 未认证的调用触发过一次限流，因此"菜单解析""社交链接抽取"两类项目的候选名单可能不完整。许可证 SPDX 显示为 NOASSERTION 的仓库，已尽量读取其 LICENSE 原文核实。项目的功能描述来自各仓库 README，没有实际运行测试。条款解读不构成法律意见。

Overture 的优势来自实测。都柏林范围内有 **2,337 家**餐厅，78.2% 的 confidence ≥0.7；阿姆斯特丹 **4,214 家**；大伦敦范围 **26,892 家**，而同一区域的 OSM 只有 9,113 家。Overture 的邮箱覆盖为都柏林 48.6%、伦敦 36.4%，OSM 在这两个城市分别只有 9.5% 和 6.0% ([Overture Places Guide](https://docs.overturemaps.org/guides/places/))。许可层面，Overture Places 按数据来源分别采用 CDLA Permissive 2.0（Meta、Microsoft 等）、Apache 2.0（Foursquare，须署名 "Data from Foursquare"）和 CC0（AllThePlaces），并且明确说明不包含 OSM 数据、不承担 ODbL 的 share-alike 义务 ([Overture Attribution](https://docs.overturemaps.org/attribution/))。使用时要注意三点。第一，**社媒字段几乎都是 `facebook.com/{数字id}`**，Instagram 很少，仍需从官网补齐。第二，邮箱大多来自 Meta，可能混有 gmail 等个人邮箱，入库时应标注来源，并单独做合规评估。第三，2026-09 版删除了 `categories` 字段，分类改用 `basic_category` 或 `taxonomy`；同一版的 `operating_status` 在所测范围内全部为 null，不能用来识别新开或关闭的门店 ([2026-09-23 release notes](https://docs.overturemaps.org/blog/2026/09/23/release-notes/))。

Foursquare 有两条产品线，性质截然不同。付费的 Places API 采用自助版 EULA，许可"可撤销、不可再许可、不得创作衍生作品"，展示时须标注 "Powered by Foursquare" ([Foursquare Places API EULA](https://foursquare.com/legal/terms/apilicenseagreement/))；按二手资料，自助账户只能长期保存 ID。开放数据集 **FSQ OS Places 采用 Apache 2.0**，字段包括 tel、website、email、facebook_id、instagram、twitter、date_created、date_refreshed、date_closed ([Places OS Data Schema](https://docs.foursquare.com/data-products/docs/places-os-data-schema))，可以通过 Places Portal、Hugging Face 门控下载或 Snowflake 获取 ([Access FSQ OS Places](https://docs.foursquare.com/data-products/docs/access-fsq-os-places))。Overture 从 2026-03 起已并入 Foursquare 数据，都柏林样本中有 323 条带 Foursquare 来源，所以单独下载 FSQ OS 的主要价值在于 `instagram` 字段和 `date_created`、`date_closed` 这两个时间字段。需要注意，官方说明 `date_created` 只是记录进入数据库的日期，"不一定是实际开业日"。FSQ OS 在欧洲的字段填充率没有公开统计，本次也没有注册实测，是下一步最值得补的一项数据。

Google 的问题在条款，费用不是障碍。全球版条款第 3.2.3 条明确禁止"copy and save business names, addresses, or user reviews"，并禁止缓存；经纬度最多缓存 30 天，只有 place_id 可以无限期保存 ([Google Maps Platform Terms](https://cloud.google.com/maps-platform/terms)；[Service Specific Terms](https://cloud.google.com/maps-platform/terms/maps-service-terms))。结算地址在 EEA 的账户适用单独条款，这里有一个此前没有注意到的细节：Places 内容只能用于 9 类白名单用途，其中第 (3) 类是"enable Customers to visualize and manage Places content related to a sales team's customers or opportunities" ([Places API EEA Permitted Uses](https://cloud.google.com/terms/maps-platform/eea-places-api-permitted-uses))。这为"CRM 只存 place_id，打开线索详情时实时拉取评分"提供了条款依据，但并不允许存储；用 Google 批量"发现"商机本身，仍有被认定为 bulk download 的灰色地带。技术上还有两个限制：Text Search 单次查询最多返回 **60 条**，铺满一个城市需要按"网格 × 菜系"切分查询；`openingDate` 只覆盖尚未开业、有预期开业日期的商家 ([Text Search (New)](https://developers.google.com/maps/documentation/places/web-service/text-search))。Places API 不返回邮箱，也没有社交或菜单字段 ([Place Data Fields](https://developers.google.com/maps/documentation/places/web-service/data-fields))。筛选 1,000–5,000 家的 API 费用约 $0–80 ([Pricing](https://developers.google.com/maps/billing-and-pricing/pricing))。

其余来源大多只能做辅助。Yelp 在 2026-09-22 更新的条款中把缓存上限定为 **24 小时**，禁止批量下载，还对直销类用途有限制，不适合建库 ([Yelp API Terms](https://terms.yelp.com/developers/api_terms/))。Mapbox Search Box 的返回结果"only available for temporary use" ([Mapbox Search Box](https://docs.mapbox.com/api/search/search-box/))。Apple Maps Server API 每天有 25,000 次免费调用 ([WWDC22](https://developer.apple.com/videos/play/wwdc2022/10006/))，可以用来交叉校验电话和网址，但本次抓取的 Place 对象中没有看到 phone 或 url 字段，需要实测确认。抓取型数据集单价最低，Bright Data 的 Google Maps 数据集最高 $0.0025/条、最低订单 $250 ([Bright Data](https://brightdata.com/products/datasets/google-maps))，但来源违反 Google 条款，买方存储后的风险要自己承担。Openmart 声称覆盖英国、爱尔兰、西班牙、法国的 50 万+ 餐厅店主联系人，$149/月起 ([Openmart](https://www.openmart.com/databases/restaurants))，但数据来源和 GDPR 说明没有核实，原方案中"不购买来源不明的名单"这一条同样适用于它。外卖平台（Deliveroo、Uber Eats 等）的菜单 API 都是"商户向平台写入"方向，只对签约伙伴开放，条款禁止复制 ([Deliveroo Developers Terms](https://developers.deliveroo.com/terms)；[Uber Eats Marketplace API](https://developer.uber.com/docs/eats/introduction))，只能记录"是否在某平台上架"这一信号。

## 官网是邮箱、WhatsApp 和菜单的唯一可靠来源

开放数据解决了"找到餐厅和电话"的问题，但 WhatsApp、菜单、负责人姓名，以及大部分可用邮箱，只能从官网获取。结构化数据帮助有限：全网 41% 的页面使用 JSON-LD，但移动端标注为 Restaurant 类型的页面只有 **0.19%**，LocalBusiness 为 3.97% ([Web Almanac 2024](https://almanac.httparchive.org/en/2024/structured-data))。Web Data Commons 2024 年的语料中，只有 84,256 个主机带 Restaurant 实体 ([WDC Schema.org Subsets](https://webdatacommons.org/structureddata/2024-12/stats/schema_org_subsets.html))。所以 JSON-LD 只能作为"命中即高置信"的加分项，主要路径是解析法定信息页面。奥地利 §5 ECG 要求联系信息（含邮箱）可以"直接"访问 ([WKO](https://www.wko.at/information-consulting/werbung-marktkommunikation/impressum-und-offenlegung))；法国 LCEN 第 6 条要求写明**出版负责人（directeur de la publication）姓名**和一种直接联系方式 ([Légifrance](https://www.legifrance.gouv.fr/loda/article_lc/LEGIARTI000044067469))；西班牙 LSSI-CE 第 10 条要求"永久、方便、直接、免费"地提供邮箱等联系方式 ([LSSI FAQ](https://lssi.mineco.gob.es/la-ley/Paginas/preguntas-frecuentes.aspx))。因此抓取顺序建议为：首页 JSON-LD → 页脚与页头中的 `tel:`、`mailto:`、`wa.me`、`api.whatsapp.com/send`、instagram.com、facebook.com 链接 → `/impressum`、`/mentions-legales`、`/aviso-legal` → `/contact`、`/kontakt`，并用 `<form>` 判断是否为联系表单 → 隐私政策页。法定页面中写明的经营者或负责人姓名，是公开渠道中最好的决策人来源，但属于个人数据，需要做合法利益评估。

菜单的存放形式没有统一规律。Wix Restaurants 支持导入 PDF（最多 100 页）、图片或 CSV，前端输出结构化 HTML ([Wix Help](https://support.wix.com/en/article/wix-restaurants-setting-up-wix-restaurants-menus-new))；Squarespace 有专门的 Menu block ([Squarespace](https://support.squarespace.com/hc/en-us/articles/206544087-Menu-blocks))。实操上，先按多语言关键词（menu、speisekarte、carte、carta）找链接，再找 `.pdf` 文件，接着找图片画廊，最后处理嵌入第三方的情况。用资源域名识别建站平台（static.wixstatic.com、squarespace-cdn、/wp-content/），再调用对应平台的专用解析器。欧洲餐厅中 HTML、PDF、图片菜单各占多少比例，没有任何公开统计，仍需在试点前抽样 100–200 家做人工标注。

WhatsApp 是原方案里假设最乐观的一项。原方案写"餐厅电话号码往往就是 WhatsApp 号码"，但这一点已经**无法用官方手段验证**：WhatsApp 旧版 contacts 端点现在对任何号码都返回 valid，On-Premises API 也已弃用 ([Meta 文档](https://developers.facebook.com/documentation/business-messaging/whatsapp/business-scoped-user-ids/))。市面上的 number checker 都依赖非官方的 WhatsApp Web 协议，违反条款，并且有封号风险。可行的做法分三级：官网或 Instagram 上公开了 `wa.me` 链接的，视为"已公开 WhatsApp"；用 libphonenumber 判断为手机号但没有公开链接的，标记为"可能"；固定电话则判定为"否"。欧洲 WhatsApp 普及率很高，荷兰 98%、意大利 97%、德国 95.5%（按即时通讯用户口径，来自二手汇总）([LINK Mobility](https://www.linkmobility.com/blog/whatsapp-use-in-europe-and-adoption-across-countries))，但"普及率高"不等于"餐厅号码开通了 WhatsApp"。

Instagram 应优先从官网获取账号名，官方 API 只用来核验。Instagram Graph API 的 Business Discovery 可以用自己的专业账号，查询其他公开的 Business/Creator 账号的 biography、website、followers_count 等字段 ([Meta Business Discovery](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-facebook-login/business-discovery/))，前提是已经知道对方的 handle，而且拿不到联系按钮里的电话和邮箱。Meta 的 Automated Data Collection Terms 要求，自动采集须事先取得书面许可 ([Meta](https://www.facebook.com/legal/automated_data_collection_terms))。美国 Meta v. Bright Data 案认定"登出状态下抓取公开数据"不违反 Meta ToS ([Courthouse News](https://www.courthousenews.com/federal-judge-rules-against-meta-in-data-scraping-case/))，但这个判例不影响欧洲的 GDPR 分析。对于官网没有链接的餐厅，需要用搜索 API 反查，而 2026 年的选择已经不多：**Bing Search API 已于 2025-08-11 下线** ([Microsoft](https://learn.microsoft.com/en-us/lifecycle/announcements/bing-search-api-retirement))；Google Custom Search JSON API 不再接受新客户，老客户只能用到 2027-01-01 ([Google](https://developers.google.com/custom-search/v1/overview))。剩下的选项是 Brave Search API（自有索引，$5/千次，但存储结果需要 Enterprise 套餐）([Brave](https://brave.com/search/api/))，以及抓取 Google 结果的 Serper、SerpApi（$25/月起）([SerpApi](https://serpapi.com/pricing))。5,000 家、每家 2–3 次查询，花费在 $10–150 之间。建议只把搜索结果当作"指针"，最终存储的是自己访问官网或 IG 后核验得到的数据。

## 政府登记提供最早的新开业信号，英国的数据组合最完整

原方案把"近期新开业、装修或更换品牌"列为筛选条件，但没有说明数据从哪里来。商业 API 基本给不出这个信号，政府登记可以。**英国 FSA 食品卫生评级数据是欧洲最好的免费底库**：全英约 61.3 万家食品经营者，每天更新，调用 API 不需要注册 ([FSA Open Data](https://ratings.food.gov.uk/open-data))。实测 Restaurant/Cafe/Canteen 类 141,026 家、Pub/bar 类 50,482 家、Takeaway 类 62,960 家。新登记的食品企业会先以 **AwaitingInspection** 状态出现（RatingDate 用 1901-01-01 占位），实测威斯敏斯特有 91 家、曼彻斯特有 497 家 ([FSA API V2](https://api.ratings.food.gov.uk/help))。这些记录多是开业前或刚开业的门店，正处在需要菜单的时间窗口。曼彻斯特的数量偏高，可能包含积压未检查的老店，需要用 FHRSID 的每日增量来识别真正的新记录。FSA 数据的缺点是**完全没有联系方式**（实测 Phone 字段填充为 0），需要按"名称 + 邮编 + 50 米距离"与 Overture 匹配来补齐。FSA ↔ Overture 的实际匹配率还没有实测，建议试点先抽样 500 家。

**Companies House 解决两个问题：法律形式和新成立公司。** 实测活跃的 SIC 56101 公司有 54,910 家；2026 年 8 月新成立 SIC 56101 公司 697 家、56102 公司 919 家 ([Companies House Advanced Search](https://find-and-update.company-information.service.gov.uk/advanced-search))。API 支持按 SIC 和成立日期筛选，单次最多返回 5,000 条 ([CH API spec](https://developer-specs.company-information.service.gov.uk/companies-house-public-data-api/reference/search/advanced-company-search))；Streaming API 可以实时推送公司和董事事件 ([CH Streaming](https://developer-specs.company-information.service.gov.uk/streaming-api/guides/overview))。这对合规很关键。PECR 规定，向公司发营销邮件不需要事先同意，而"sole traders and some partnerships are treated as individuals" ([ICO](https://ico.org.uk/for-organisations/direct-marketing-and-privacy-and-electronic-communications/guide-to-pecr/electronic-and-telephone-marketing/electronic-mail-marketing/))。所以规则可以写成：在 Companies House 匹配到 Ltd 的，可以发 B2B 邮件；匹配不到的，按个体户处理，只用电话、实物样品和官网联系表单。要注意"公司成立"不等于"开店"，注册地址常常是会计师的地址，必须与 FSA 的 AwaitingInspection 名单交叉核对。另一个信号源是地方议会的酒类场所许可登记。《2003 年许可法》要求议会公示新申请，Bexley、Broxtowe 等议会提供 CSV 下载 ([Bexley](https://www.bexley.gov.uk/bexley-business-employment/business-services/licensing-and-permits/public-licensing-register/registers-you-can-download))，但全国没有统一数据集，只能按区逐个抓取。

其他国家的数据情况各不相同，再叠加上一轮确认的合规分区，就得到下面的试点排序。合规分区的结论是：英国、爱尔兰、荷兰、法国、比利时的法人通用邮箱采用 opt-out 规则；德国、奥地利、西班牙、意大利、波兰、丹麦对企业邮箱也要求事先同意 ([DLA Piper Spain](https://www.dlapiperdataprotection.com/index.html?t=electronic-marketing&c=ES)；[IT-Recht Kanzlei](https://www.it-recht-kanzlei.de/b2b-e-mail-marketing-unterlassung-schadensersatz-uwg-dsgvo.html))。

| 国家 | 底库 | 联系方式补全 | 法律形式 / 决策人 | 新开业信号 | 邮件合规 | 推荐度 |
|---|---|---|---|---|---|---|
| **英国** | FSA（全量，每日更新） | Overture + 官网 | Companies House（Ltd / 个体户、董事） | FSA AwaitingInspection、CH 新成立公司、议会许可 | 法人 opt-out | **首选** |
| 爱尔兰 | Overture（都柏林 2,337 家） | 官网 | CRO 开放数据（CC BY 4.0，含 NACE）([CRO](https://cro.ie/the-companies-registration-office-cro-announces-the-launch-of-new-open-data-portal/)) | 仅 CRO 新成立公司；FSAI 没有公开名册 ([FSAI](https://www.fsai.ie/re-use-of-public-sector-information)) | opt-out | 备选 |
| 法国 | SIRENE（门店级） | Overture + 官网 | mentions légales 中的出版负责人 | **SIRENE `dateCreationEtablissement`**，按门店记录，每日更新 ([data.gouv.fr](https://www.data.gouv.fr/datasets/base-sirene-des-entreprises-et-de-leurs-etablissements-siren-siret)) | opt-out，但 CNIL 较严 | 第二阶段 |
| 荷兰 | Overture（阿姆斯特丹 4,214 家）+ OSM | 官网（OSM 官网覆盖 66%） | KvK（€6.40/月 + €0.02/次）([KVK](https://developers.kvk.nl/nl/pricing)) | 没有免费全量名册；NVWA 不提供下载 | opt-out | 第二阶段 |
| 丹麦 | Smiley（23,353 家，99.7% 带 CVR）([Smiley XML](https://www.foedevarestyrelsen.dk/Media/638212360788086849/Smiley_xml.xml)) | Overture + 官网 | CVR | 677 家尚无检查日期 | 需事先同意 | 不做邮件 |
| 德、奥、西、意 | Overture / OSM | 官网（Impressum 最容易拿到邮箱） | Impressum | 没有全国公开名册 | **需事先同意** | 暂不纳入 |

法国有两个细节需要提前处理。一是 NAF 2025 改版，从 2027-01-01 起，56.10A 改为 56.11G，快餐拆分为 56.11J 和 56.12Y ([INSEE NAF 2025](https://www.insee.fr/fr/information/8181066))，查询条件要同时兼容新旧代码。二是选择"diffusion partielle"的个人企业，姓名和地址会被遮蔽。丹麦 Smiley 数据中 `reklame_beskyttelse=1` 的 105 家明确拒绝广告，这个字段应当直接作为屏蔽名单的模板。英国管线的全部数据源都免费，成本只在工程上：Overture 按国家下载 1–2 个 Parquet 分片即可，FSA 和 Companies House 只需要每天同步。

## 开源组件覆盖采集和渲染，获客核心逻辑仍需自研

逐层检查后发现一个明显的规律：**底层组件成熟、许可证干净，但"餐厅获客"这个组合场景没有可以直接用的开源项目。** 组合型的 lead-gen 仓库普遍只有几十颗星、单人维护。与本项目最接近的 KarlvonPoncet/vienna-restaurant-leads 没有许可证，代码不能复用 ([GitHub](https://github.com/KarlvonPoncet/vienna-restaurant-leads))。架构上最值得参考的是 moasq/leadshoot（MIT）：默认使用 OSM，接入 Overture，Google 通过 gosom 作为可选项，再加上官网核验和 MCP，整体思路与本报告的建议一致，但它只有 6 颗星、10 次提交，不能作为依赖 ([leadshoot](https://github.com/moasq/leadshoot))。菜单解析方向，按星数搜索只能找到个位数星的 demo ([GitHub 搜索](https://github.com/search?q=restaurant+menu+llm&type=repositories))。AI SDR 方向，最有名的 SalesGPT 最近一次推送是 2024-09-17，已经停更两年 ([SalesGPT](https://github.com/filip-michalsky/SalesGPT))。开源冷邮件工具中唯一功能完整的是 warmbly（Apache-2.0，319 星），项目还很年轻 ([warmbly](https://github.com/warmbly/warmbly))。

按模块整理的复用与自研划分如下（stars 为 2026-09-25 的快照）：

| 模块 | 直接复用 | 许可证 | 自研部分 |
|---|---|---|---|
| 餐厅发现 | [overturemaps-py](https://github.com/OvertureMaps/overturemaps-py)（270★）+ DuckDB；[quackosm](https://github.com/kraina-ai/quackosm)（375★）读 OSM | MIT / Apache-2.0 | FSA、CH、SIRENE 同步任务；多源去重；实体匹配 |
| 官网爬取 | [crawl4ai](https://github.com/unclecode/crawl4ai)（84.3k★），或 [crawlee-python](https://github.com/apify/crawlee-python) + [playwright](https://github.com/microsoft/playwright) | Apache-2.0（crawl4ai 要求在文档中致谢） | 多语言路径规则；静态抓取失败时回落到浏览器渲染 |

| 邮件触达 | 模板用 [MJML](https://github.com/mjmlio/mjml)、[react-email](https://github.com/resend/react-email)；warmbly 只做 PoC 对照 | MIT / Apache-2.0 | 试点期接 Smartlead/Instantly API，或自建轻量序列表 |

许可证风险集中在五类项目，交付前都要逐一排查。**第一类是 AGPL/GPL**：Firecrawl（AGPL-3.0，自托管还需要 Redis、RabbitMQ、PostgreSQL 等多个服务）([firecrawl](https://github.com/firecrawl/firecrawl))、PyMuPDF（AGPL）、reacher 的 SMTP 邮箱验证（AGPL 或商业许可双授权）([reacher](https://github.com/reacherhq/check-if-email-exists))、nodriver（AGPL）、listmonk、BillionMail、EspoCRM、SuiteCRM、Frappe CRM（均为 AGPL），以及 Mautic、theHarvester（GPL）。如果修改后以网络服务形式提供给客户，就要开放源码。**第二类是 fair-code 或源码可见许可**。n8n 的 SUL 允许"在你的实例上为客户构建自动化，只要客户不能创建或编辑"，禁止白标，也禁止让客户自己搭建工作流 ([n8n License FAQ](https://docs.n8n.io/n8n-community-license/community-license/license-faq))。NocoDB 自 2026-01 起从 AGPL 改为 SUL ([NocoDB License](https://nocodb.com/docs/self-hosting/license))。Carbone 社区版禁止以"文档生成即服务"的形式提供 ([carbone](https://github.com/carboneio/carbone))。**第三类是模型权重附加条款**。Marker 的代码是 Apache，但权重只对收入或融资低于 500 万美元的公司免费 ([marker](https://github.com/datalab-to/marker))；MinerU 要求在线服务"显著注明"使用了 MinerU ([MinerU LICENSE](https://github.com/opendatalab/MinerU/blob/master/LICENSE.md))。**第四类是违反平台条款的工具**，许可证本身写着 MIT，但使用行为违约。gosom 等 Google Maps 抓取器违反 Google 条款；Baileys 和 Evolution API 的 Baileys 模式违反 WhatsApp 条款，有封号风险 ([Baileys](https://github.com/WhiskeySockets/Baileys))。**第五类是数据许可**。OSM 的 ODbL 在对外分发衍生数据库时要求共享；Overture 的 Foursquare 部分须署名；法国 SIRENE 使用须符合 GDPR；FSA 数据是否采用 OGL v3 还没有找到条款原文。按 Twenty 的 LICENSE，Twenty CRM 附带一条 API 例外，通过 API 集成的应用不受 AGPL 约束 ([Twenty LICENSE](https://github.com/twentyhq/twenty/blob/main/LICENSE))，所以如果客户想要独立的 CRM，可以选它作为外部同步目标。

## 对原方案三处的具体修改建议

### "1 发现目标餐厅"：从"按条件搜索"改为"底库 + 信号 + 实时补充"

原文的问题有三个。一是把 Google Places 放在数据来源首位，但它的数据不能存储。二是"价格区间、评论数和评分"这两个筛选条件，只能来自禁止存储的 API。三是"近期新开业"没有给出任何数据来源。建议把本节改写为三层结构：

| 层级 | 用途 | 数据来源（试点：英国） | 存储方式 |
|---|---|---|---|
| 底库 | 国家、城市、菜系、是否有官网、地址 | FSA 全量（餐厅/酒吧/外卖三类）+ Overture Places（`basic_category` 属于 restaurant、bar、cafe，confidence ≥0.6）；OSM 作交叉校验 | 可存；每条记录保存来源、许可、版本号 |
| 信号 | 新开业、易主、更换品牌 | FSA 新增 FHRSID 且状态为 AwaitingInspection；Companies House 新成立 SIC 56101/56102；议会场所许可的新申请或转让；Overture 相邻版本新增的 GERS id；FSQ OS 的 `date_created` | 可存；每日或每周增量 |
| 实时补充 | 评分、评论数、价位、营业状态 | Google Places（CRM 只存 place_id，打开详情页时实时拉取，EEA 账户依据白名单第 3 类，不与地图同时展示）；可选 Tripadvisor 或 Foursquare Premium 实时拉取 | 不入库；评分只在打开详情页时显示，不作为批量筛选条件 |

同时删去"优先使用官方 API"这种笼统表述，改为：**"优先使用许可允许存储的开放数据和政府登记；商业 API 只做实时展示；不使用抓取 Google Maps 的工具或数据集。"** 如果评分必须参与排序，在 EEA/UK 账户下应先请法务确认，"批量拉取评分用于排序"是否超出白名单第 (3) 类，否则改用"评论数的替代信号"（例如 Overture confidence、是否有官网、社媒是否活跃）。另外要注意，Text Search 每次查询最多返回 60 条，所以 Google 不能用作城市级的全量发现源。

### "2 采集多渠道联系方式"：纠正来源，加上"可否入库"和"合规分层"两列

建议用下表替换原表：

| 联系方式 | 主要来源（按优先级） | 可否入库 | 覆盖率参考 | 说明 |
|---|---|---|---|---|
| 电话 | Overture → 官网 → FSQ OS | 可以 | Overture 89–93% | Google 电话只做实时核对，不入库 |
| WhatsApp | 官网或 IG 上的 `wa.me`、`api.whatsapp.com/send` 链接 | 可以 | OSM 仅 0.07%，官网比例未知 | 分"已公开 / 可能（手机号）/ 否"三级；**删除"电话往往就是 WhatsApp"的表述**；禁用号码检测工具 |
| Instagram | 官网 sameAs 或页脚 → FSQ OS `instagram` → 搜索 API 反查 → IG Business Discovery 核验城市和名称 | 可以（只存 handle） | Overture 社媒几乎都是 Facebook；OSM 为 1.66% | 删去原文中"OSM `contact:instagram`"作为主要来源的写法 |
| Facebook | Overture `socials` → 官网 | 可以 | Overture 80–93% | |
| 邮箱 | 官网法定页面（Impressum、mentions légales、aviso legal）→ 联系页 → 隐私政策页 → Overture `emails` | 可以（标注来源 URL） | Overture 36–53%，需剔除个人邮箱 | 用 email-validator 做语法和 MX 校验；catch-all 地址单独分组 |
| 联系表单 | 官网 `/contact`、`/kontakt`，含 `<form>` | 可以 | 未知 | |
| 实体地址 | FSA、SIRENE、Overture | 可以 | FSA 全量 | **不用 Google 地址**（条款禁止保存） |
| 法律形式 | Companies House / CRO / SIRENE / KvK | 可以 | — | **新增字段**：法人可发邮件，个体户只用电话、样品和表单 |
| 负责人姓名 | CH 董事、法国出版负责人、德奥 Impressum 中的 Inhaber | 可以（需合法利益评估） | — | 删去"荷兰 KvK 免费获取"的暗示，KvK 按次收费 |
| 菜单 | 官网 HTML、PDF、图片；JSON-LD `hasMenu` | 可以 | 格式分布需抽样 | 外卖平台只记录"是否上架"，不抓取菜单 |
| 评分、价位 | Google、Tripadvisor 实时拉取 | **不可以** | — | 只在线索详情页显示 |
| 屏蔽标记 | 丹麦 `reklame_beskyttelse` 等官方拒收标记、退订记录 | 可以 | — | 采集时直接写入禁止联系名单 |

原文"Google 地图聊天已关闭""订位和外卖平台不作为触达渠道"两句可以保留。建议在"3 建立餐厅线索档案"中同步新增四个字段：法律形式、`source_license`（数据许可）、`storable`（是否允许存储）、`whatsapp_confidence`（WhatsApp 置信度）。

### 技术架构：去掉重复的编排层，新增开放数据层，写明许可证边界

| 层级 | 原方案 | 修改建议 |
|---|---|---|
| 开放数据层（新增） | 无 | DuckDB + overturemaps-py 读取 Overture Parquet（按国家下载分片）；定时任务同步 FSA、Companies House、SIRENE；quackosm 读取 OSM |
| 采集与抽取（新增） | 仅"Redis、Celery 抓取" | 优先用 httpx/curl_cffi 静态抓取，遇到 Wix 或空壳 SPA 时回落到 crawl4ai 或 Playwright；用 extruct、phonenumbers、email-validator 抽取和校验；同一域名 ≤1 次请求/秒，遵守 robots.txt；每 90 天刷新一次 |
| 菜单解析（新增） | 可替换的模型接口 | HTML 直接取文本，PDF 用 Docling，图片用多模态 LLM 或 PaddleOCR，最后用 Instructor 按 schema 抽取；**不使用 PyMuPDF（AGPL）**；Marker 和 MinerU 须经许可评估后才可启用 |
| 工作流 | n8n | **从核心中移除**。编排统一用 Celery + beat（与上一轮建议一致，避免维护两套队列）；n8n 只可作为客户自托管的内部通知胶水，不能让客户在其中编辑工作流 |
| 邮件 | Google Workspace 或 M365 直接发送 | 试点期接 Smartlead/Instantly API，关闭预热网络；如需自研，用 Celery 序列表 + Gmail/Graph API，模板用 MJML |
| 样品生成 | HTML 模板渲染为 PDF/PNG | 明确使用 Next.js 模板 + Playwright，或 Gotenberg 微服务；印刷文件的 CMYK 和出血用 Typst 实测后再定；不使用 Carbone 社区版和 wkhtmltopdf（已归档） |
| 前端与 CRM | Next.js、Ant Design | 保留自研；数据模型参考 Atomic CRM（MIT）；客户如需独立 CRM，通过 API 同步到 Twenty 或 Krayin |
| 数据库 | PostgreSQL | 增加字段级来源和许可记录；Google、Yelp、Foursquare 付费 API 的字段只放在缓存层，设置 TTL，不写入主表 |
| 部署 | Docker Compose | 服务器放在英国或欧盟区域；CI 中加入依赖许可证扫描，拦截 AGPL、GPL、SUL 依赖 |

工作量方面，开放数据层和官网抽取替代了原来的"Google 采集"，同时新增了实体匹配和政府登记同步，"餐厅采集与多渠道联系方式"一项建议从 5–8 人日调整为 7–10 人日（本报告估算，没有外部基准）。去掉 n8n、接入发信 SaaS 可以抵消这部分增加。

## 结论

这轮调研改变了对"数据从哪里来"的基本判断。开放数据的质量已经足够好，付费 API 反而最不适合拿来建线索库。Overture 在联系字段上碾压 OSM，许可也比 Google 宽松得多，这意味着试点的数据成本可以压到接近零，预算应当转到官网抽取的工程质量和人工抽检上。另一个意外发现是，英国的食品卫生登记和公司登记可以同时回答三个问题：这家店是不是刚开，是不是法人，能不能发邮件。它们把"新开业"这一原方案中最模糊的筛选条件，变成了每天自动更新的名单，而新开业的餐厅正是最需要菜单的客户。

真正仍然未知的，是官网这一层的实际产出：多少餐厅能解析出菜单、多少会公开 `wa.me` 链接、FSA 与 Overture 能匹配上多少。这三个比例决定了多渠道触达是否成立，没有任何公开统计可以代替。所以试点第一周应该做的不是发信，而是在伦敦抽取 500 家 FSA 记录，完整跑一遍"匹配 Overture → 抓取官网 → 抽取渠道和菜单"，用实测比例校准评分权重和渠道节奏。开源生态能帮忙完成搬运和解析，判断哪家餐厅值得联系、以什么顺序在哪个渠道联系，仍需要系统自己完成，这也是这套系统唯一难以被复制的部分。
